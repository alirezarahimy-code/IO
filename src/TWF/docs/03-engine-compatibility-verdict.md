# ۰۳ — حکم سازگاری موتور (Engine Compatibility Verdict) و قفل نسخه

**تاریخ:** ۱۴۰۴/۰۸/۰۳ (2026-10-25)
**دامنه:** `TWF 4.28` (نسخه قدیمی)، `T5Web [3.5.7]`، `T5V3.9.2` — سه نسخه‌ای که در مخزن موجودند
**ابزارها:** `tools/analyze-engine.py`، `tools/verify-engine-pin.py`، `engine/engine-pin.json`
**خلاصه یک‌خطی:** آریا فقط و فقط روی موتور **t5web-3.5.7** ساخته می‌شود؛ این نسخه به‌صورت ماشینی قفل و در بیلد اجباری شده است.

---

## ۱. چرا اصلاً «قفل نسخه» لازم شد

آریا مالک اسکیمای پایگاه‌داده نیست (بند R1 در `docs/02-shared-database-contract.md`). موتور T5 (`T5V3.DB.dll` و خانواده `T5V3.*`) هم مالک اسکیما است و هم منطق محاسباتی مرخصی/حضور را در اختیار دارد. اگر نسخه موتور روی سرور مشتری عوض شود:

* ممکن است یک متد یا پراپرتی که آریا صدا می‌زند حذف شده باشد ← `MissingMethodException` در وسط شیفت؛
* یا بدتر: همان متد وجود داشته باشد ولی **معنای محاسبه** عوض شده باشد ← عدد مرخصی اشتباه، بدون هیچ خطایی.

مورد دوم خطرناک‌تر است چون هیچ تستی آن را نمی‌گیرد؛ پس علاوه بر «قفل نام و امضا»، باید **اثبات بایت‌به‌بایت** برای اسمبلی‌های محاسباتی داشته باشیم.

---

## ۲. نتیجه تحلیل سطح API

`tools/analyze-engine.py` سطح API هر سه بیلد را از روی متادیتای .NET استخراج می‌کند و «مجموعه اعضای گمشده» را **فقط نسبت به خط پایه (`TWF 4.28`)** می‌سنجد. سپس هر فراخوانی آریا را در دو گذر بررسی می‌کند:

1. **فراخوانی مستقیم** — `Type.Member`
2. **فراخوانی زنجیره‌ای از پراپرتی مدیر** — `DB.TitlesCharts.GetAllGuardAccess` (این گذر دوم حیاتی بود؛ بدون آن، فراخوانی‌های زنجیره‌ای دیده نمی‌شدند و حکم به‌غلط «سازگار» بود)

| بیلد | حکم | توضیح |
|---|---|---|
| `twf-4.28` | **COMPATIBLE** | خط پایه؛ همان بیلدی که آریا از رویش نوشته شد |
| `t5web-3.5.7` | **COMPATIBLE** | تنها افت سطح API: `ProgramAccess.{freeremain, reportreq, reserve}` — آریا هیچ‌کدام را صدا نمی‌زند |
| `t5v3-3.9.2` | **INCOMPATIBLE** | `DB.TitlesCharts.GetAllGuardAccess` وجود ندارد |

### شکست `t5v3-3.9.2` — دقیقاً کجا؟

| محل فراخوانی | خط |
|---|---|
| `TWF.Web/Controllers/LeavesReportController.cs` | ۷۷ |
| `TWF.Infrastructure/Adapters/T5V3BackendAdapter.cs` | ۱۸۳ |

علاوه بر آن، `3.9.2` این‌ها را هم ندارد (جمعاً ۳۳ عضو): `CustomWFDA`، `EntityClasses.CustomWorkflow`، `Model.CustomWF`، `Personnel.Dbcon`، `PhotoFace`، `ZK.PhotoFolder`، `DBManager.UpdateDB`، `TitlesChart.GuardAccess`، `TitleChartDA.GetAll|SetGuardAccess`.

> **نکته مهم درباره `DB.EntityManagers`:** این زنجیره در هر سه بیلد «پراپرتی موجود نیست» می‌دهد، یعنی در سورس آریا یک زنجیره حل‌نشده است و **رجسیون نیست**. باید در بازبینی بعدی سورس تمیز شود، ولی روی حکم سازگاری اثر ندارد.

فرمان بازتولید:

```bash
cd src/TWF
python3 tools/analyze-engine.py --json /tmp/engine.json
```

## ۳. اثبات پاریتی محاسباتی (نه فقط سطح API)

حتی وقتی امضاها یکی باشند، دو بیلد می‌توانند محاسبه متفاوتی داشته باشند. بنابراین اسمبلی‌هایی که ریاضیات مرخصی و حضور را انجام می‌دهند بایت‌به‌بایت مقایسه شدند:

```
python3 tools/verify-engine-pin.py --equality "/home/user/IO/TWF 4.28/App/bin"
```

| اسمبلی | نتیجه |
|---|---|
| `T5V3.Attendance.dll` | **IDENTICAL** |
| `T5V3.LeaveCalcs.dll` | **IDENTICAL** |

**نتیجه:** جابه‌جایی موتور از `twf-4.28` به `t5web-3.5.7` **نمی‌تواند** عدد حضور یا مانده مرخصی را تغییر دهد. این تنها ادعایی است که با شواهد بایتی پشتیبانی می‌شود.

### قفل چگونه «اجباری» شد (نه فقط مستند)

| لایه | مکانیزم |
|---|---|
| ارجاع‌های پروژه | تمام `HintPath`ها در `TD5`، `TWF.Application`، `TWF.Infrastructure`، `TWF.Web` به `T5Web [3.5.7]\App\bin` تغییر کرد؛ هیچ ارجاعی به `TWF 4.28\App\bin` نمانده |
| اسکریپت بیلد | `build-and-test.sh` مسیر موتور را از `engine-pin.json` می‌خواند، نه از مسیر hard-code شده |
| تست خودکار | `TEST-44` هر `HintPath` بیرون از پوشه قفل‌شده را **شکست** می‌دهد |
| لینتر | `tools/lint-csharp.py` هر فراخوانی `EngineType.Member` را با سطح API بیلد قفل‌شده تطبیق می‌دهد |

## ۵. پیامدهای مهندسی (الزامی برای آریا)

1. **ممنوع:** `CustomWF*`، `Personnel.Dbcon`، `PhotoFace`، `ZK.PhotoFolder`، `DBManager.UpdateDB`، `TitlesChart.GuardAccess` — در `3.9.2` وجود ندارند و در `3.5.7` هم نباید به آن‌ها وابستگی جدید ساخت.
2. **ممنوع:** `ProgramAccess.freeremain` / `reportreq` / `reserve` — در هر دو بیلد وب حذف شده‌اند.
3. **الزامی:** هر ارتقای موتور در محل مشتری باید اول `verify-engine-pin.py --check` بدهد؛ اگر `DIVERGENT` شد، آریا نباید بالا بیاید تا تصمیم تیم مدیریت.
4. **الزامی:** نسخه موتور در قرارداد پایگاه‌داده (R5) به همین `engine-pin.json` ارجاع می‌دهد، نه به شماره نسخه دستی.

## ۶. محدودیت‌های این حکم (صادقانه)

* در این محیط `csc`/`dotnet`/`mono` و SQL Server وجود ندارد؛ پس هیچ‌کدام از این بررسی‌ها **اجرا** نشده‌اند، بلکه روی متادیتای واقعی اسمبلی‌ها و روی سورس انجام شده‌اند. تحلیل متادیتا قطعی است (bytes، نه حدس)، اما «بیلد سبز» باید یک‌بار روی ماشین ویندوزِ تیم تأیید شود.
* سطح API از روی نام‌های متادیتا سنجیده می‌شود؛ تغییر «رفتار» یک متد با امضای یکسان فقط با `--equality` روی اسمبلی‌های محاسباتی و تست‌های عددی `TWF.Tests` گرفته می‌شود.
* `T5V3.9.2` ممکن است در آینده اسکیمای پایگاه‌داده را هم تغییر دهد؛ این ابزار اسکیما را نمی‌سنجد. برای اسکیما `SchemaGuard` و `db/verify-schema.sql` هست (سند ۰۵).
