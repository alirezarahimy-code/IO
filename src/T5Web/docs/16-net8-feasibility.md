# ارتقا به .NET 8 — آنچه اندازه‌گیری شد، نه آنچه حدس زده می‌شود

**سؤال:** «حالا که سورس داریم و درگیر اسمبلی نیستیم، نمی‌شود روی .NET 8 رفت؟»

**پاسخ کوتاه:** بله — و دلیلِ اصلی‌ای که تا امروز «نمی‌شد»، **غلط** بوده است. ولی
مهاجرت یک تصمیم است، نه یک تنظیم؛ این سند هر دو طرف را با عدد نشان می‌دهد.

---

## ۱. اولین چیزی که باید تصحیح شود

فرض رایج (که در `docs/10` و در توضیح app pool ۳۲-بیتی هم آمده بود) این بود:
«بازنویسی به اسمبلی‌های موتور وابسته است، پس باید روی .NET Framework و x86 بماند».

شمارش واقعی `using` در سه لایهٔ پایین:

| چه چیزی | تعداد فایل |
| :-- | --: |
| کل فایل‌های `Domain` + `Application` + `Data` | **۴۹** |
| فایل‌هایی که به موتور (`Personnel` / `T5V3`) وابسته‌اند | **۱** |
| فایل‌هایی که `System.Web` دارند | **۰** |
| فایل‌هایی که `System.Configuration` دارند | **۰** |
| فایل‌هایی که `System.Drawing` / `Registry` / `DllImport` دارند | **۰** |
| فایل‌هایی که مستقیم `SqlClient` صدا می‌زنند | **۰** (فقط `System.Data` interface) |

آن یک فایل: `T5Web.Data/Engine/PersonnelEngineDirectory.cs` — که از `Personnel.DB.*DA`
چهار فهرست می‌خواند (دپارتمان، سمت، نوع استخدام، دستگاه) و بقیهٔ کار با Dapper و SQL است.

**یعنی وابستگی به .NET Framework = یک کلاس، نه یک معماری.**

## ۲. اثباتشده با کامپایلر (اجرا شد)

Job تازهٔ `net8-spike`:

```
NET8 coupling | core files 49 | engine-coupled 1 | System.Web 0 | System.Configuration 0
NET8 build    | errors 0 | warnings 0
```

هیچ‌کدام از این‌ها روی کاغذ نیست: همین سه لایه با `TargetFramework=net8.0`،
`LangVersion=7.3` و تنها بستهٔ `Dapper` **روی یک runner لینوکسی** کامپایل شد و صفر
خطا و صفر اخطار داد. پروژهٔ واقعی: `spike/net8/Net8Spike.csproj` — که فایل‌ها را با
مسیر ارجاع می‌دهد، نه کپی، و اگر فایل دومِ موتوروابسته ظاهر شود خودِ job قرمز می‌شود.

**این جملهٔ مهم:** «نگه‌داشتن .NET Framework برای داده لازم نیست» — داده همین حالا
.NET 8 است، فقط در یک پروژه بسته‌بندی نشده بود.

## ۳. آنچه مانده: لایهٔ وب (اندازه‌گیری‌شده، هنوز کامپایل‌نشده)

| مورد | تعداد | در .NET 8 |
| :-- | --: | :-- |
| `using System.Web.Mvc` | ۲۳ فایل | `using Microsoft.AspNetCore.Mvc` — یک جست‌وجوی سراسری |
| `ActionResult` | ۶۴ مورد در ۲۲ فایل | هست، بدون تغییر |
| `ViewBag` | ۵۶ مورد در ۱۸ فایل | هست، بدون تغییر |
| `[ValidateAntiForgeryToken]` | ۱۸ مورد در ۱۲ فایل | هست؛ فقط `<form>` باید توکن را با tag helper بفرستد |
| `HttpNotFound(...)` | ۱۶ مورد در ۶ فایل | `NotFound()` |
| `HttpContext.Current` | ۲ مورد، ۱ فایل | `HttpContextAccessor` |
| `HttpPostedFileBase` | ۱ مورد | `IFormFile` |
| `ConfigurationManager` | ۶ مورد، ۴ فایل | بستهٔ `System.Configuration.ConfigurationManager` روی net8 هم کار می‌کند — پل کم‌هزینه |
| `AdminAuthorize.cs` + `BootstrapFilter` | ۵۲۷ خط، ۱ فایل | **کار واقعی**: `AuthorizeAttribute`/`ActionFilterAttribute` در Core امضاهای مختلف دارند |
| `MvcApplication.cs` (`HttpApplication`) | ۱۵۷ خط | → `Program.cs` + DI + middleware |
| نماها | ۳۴ `cshtml` | عمدتاً سازگار؛ `_ViewStart`، `_Layout`، `@Html.AntiForgeryToken`، `@Url.Action` همه هستند |
| `T41` (پارس نماها) | ۱ آزمون | `System.Web.Razor` می‌رود؛ `Microsoft.AspNetCore.Razor.Language` جای آن |
| میزبانی | — | `AspNetCoreModuleV2` + Windows Authentication + `[Authorize]` روی IIS |

## ۴. سه کار مستقل از تصمیم .NET 8 (به ترتیب ارزش)

### کار ۱ — از شر `PersonnelEngineDirectory` خلاص شو (ارزش فوری، هیچ ربطی به .NET 8 ندارد)

این فایل:
* تنها دلیلی است که **app pool باید ۳۲-بیتی** بماند (`CLR_32BITREQUIRED`)؛
* تنها دلیلی است که **`T5Web [3.5.7]\App\bin` باید روی سرور موجود باشد** و در CI پین می‌شود؛
* تنها دلیلی است که **یک وصلهٔ موتور می‌تواند پورتال را بشکند**.

در عوض، ۴ کوئری SELECT از `Personnel` (که اسکیمایش در `engine/column-types.json` و
`db/schema-manifest.json` اثبات‌شده است) همان چهار فهرست را می‌دهد. سود فوری:
**app pool ۶۴-بیتی، بدون وابستگی به اسمبلی موتور، و یک قدم نزدیک‌تر به .NET 8.**
هزینه: یک فایل + آزمون‌هایی که امروز «خواندن از DA موتور» را می‌سنجند.

### کار ۲ — پل `ConfigurationManager` و antiforgery (کوچک)

اگر تصمیم به مهاجرت گرفتید، این دو کم‌هزینه‌ترین‌اند و می‌شود از الان در Framework هم
آماده کرد (مثلاً پوشاندن تنظیمات در یک واسط `ISettings`).

### کار ۳ — مهاجرت وب (تصمیم واقعی)

| گزینه | چه می‌دهد | هزینهٔ تقریبی |
| :-- | :-- | :-- |
| **بمان روی 4.7.2** | صفر کار؛ همه‌چیز امروز اثبات‌شده | — |
| **4.7.2 + حذف وابستگی موتور** | app pool ۶۴-بیتی، استقرار ساده‌تر، بدون pin اسمبلی | کار ۱ (کوچک) |
| **net8.0 (Core)** فقط برای سرویس/ابزار | یک Windows Service روی net8 برای کارهای پس‌زمینه (صف دستور، پشتیبان) | کوچک، و مسیر مهاجرت را باز می‌کند |
| **net8.0 کامل برای وب** | پشتیبانی بلندمدت، بدون IIS کلاسیک، استقرار self-contained | لایهٔ وب: ~۳۵ فایل + ۳۴ نما + آزمون‌ها؛ یک تا دو موج کاری |

## ۵. ریسک‌هایی که باید گفته شوند

1. **SQL Server و درایور**: امروز `System.Data` + Dapper با `SqlConnection` در لایهٔ وب
   ساخته می‌شود؛ در Core باید `Microsoft.Data.SqlClient` باشد (نام‌فضا عوض می‌شود،
   رفتار تقریباً یکی است، ولی `Encrypt=True` پیش‌فرض شده — روی سرور بدون گواهی باید
   صریح تنظیم شود).
2. **Windows Authentication**: در Core روی IIS نیاز به `authentication` در `Web.config`
   و `[Authorize]` دارد؛ `AdminGate` ما با `HttpContext.User` کار می‌کند، پس منطق
   دسترسی دست‌نخورده می‌ماند ولی فیلتر بازنویسی می‌شود.
3. **آزمون `T41`**: پارس نماها با `System.Web.Razor` تمام می‌شود؛ جایگزینش روی net8
   `Microsoft.AspNetCore.Razor.Language` است. این آزمون باید بازنویسی شود — یعنی
   **گیتی که امروز ۳۴ نما را می‌سنجد، در مهاجرت اول از دست می‌رود**؛ باید قبل از
   مهاجرت جایگزین شود، نه بعد.
4. **حسابرسی/لاگ**: `HttpContext.Current` تنها در فیلتر است؛ انتقال‌اش ساده است ولی
   هر جای دیگری که ننوشته `HttpContext.Current` باشد و از راه `ThreadStatic` کار کند،
   در Core بی‌صدا خراب می‌شود. (شمارش کردیم: ۲ مورد، هر دو در یک فایل.)
5. **.NET Framework همچنان لازم است** برای دسکتاپ T5V3 و Link5 — مهاجرت وب آن‌ها را
   از معادله خارج نمی‌کند. اگر هدف «یک سرور بدون .NET Framework» است، این هدف با
   مهاجرت وب به دست نمی‌آید.

## ۶. توصیه

**امروز مهاجرت نکنید؛ ولی وابستگی موتور را بردارید (کار ۱).** دلیل:

* کار ۱ یک سود فوری و مستقل دارد (۶۴-بیتی، حذف pin، استقرار ساده‌تر) و ریسکش کم است؛
* بعد از کار ۱، «.NET 8» یک **انتخاب زیرساختی** می‌شود نه یک اجبار معماری — و در آن
  نقطه می‌شود با چشم باز تصمیم گرفت؛
* اگر قبل از کار ۱ مهاجرت کنید، هم‌زمان دو ریسک را روی هم می‌گذارید: تغییر پشته **و**
  وابستگی به اسمبلی x86 که در Core اصلاً بارگذاری نمی‌شود. یعنی مهاجرت به .NET 8
  **کار ۱ را اجبار می‌کند**، پس بهتر است اول آن انجام شود.

**آنچه امروز اثبات شده:** داده و منطق روی net8 با صفر خطا کامپایل می‌شوند.
**آنچه اثبات نشده:** لایهٔ وب روی net8 کامپایل نشده، هیچ نما/مسیر/احراز هویتی روی
net8 اجرا نشده، و هیچ آزمونی روی net8 اجرا نشده. تا آن روز، «مهاجرت‌پذیر» یعنی
«مانعی در معماری نیست»، نه «مهاجرت انجام شده».
