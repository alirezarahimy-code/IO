# ۱۲ — انتقال داده: آیا جداول یکی است و دادهٔ سامانهٔ قدیم چطور منتقل می‌شود

این سند به دو پرسش پاسخ می‌دهد:

1. جداول و پایگاه‌دادهٔ بازنویسی‌ها با نسخهٔ اولیه یکی است و به آن وفادار مانده؟
2. اگر بخواهیم دادهٔ سامانهٔ قدیم را به سامانهٔ جدید بیاوریم، دقیقاً چه کاری و به چه ترتیبی؟

خلاصه در سه خط:

* **هیچ اسکیمای تازه‌ای ساخته نشده و هیچ ستونی به جدول‌های موتور اضافه نشده.** هر دو بازنویسی
  (`TWF`/آریا و `T5Web`/آریا ادمین) به **همان دو پایگاه‌دادهٔ نصب‌شدهٔ T5V3** وصل می‌شوند.
* بنابراین «انتقال داده» در حالت عادی **صفر** است: پورتال را نصب می‌کنید و همان داده را می‌بیند.
  انتقال واقعی فقط وقتی لازم است که **سرور** یا **سازمان** عوض شود.
* هر انتقال، یک **گیت اثبات** دارد: اثر انگشت داده (`tools/migration-fingerprint.py`) پیش و پس از
  جابه‌جایی، به‌علاوهٔ `db/03-relations.sql` و `db/verify.sql`.

## ۱. پاسخ کوتاه: بله، همان پایگاه‌داده است

| کاتالوگ | نقش | کلید پیکربندی | مالک اسکیما |
| :-- | :-- | :-- | :-- |
| `ReportT5V3` | تردد، درخواست، گردش کار، تقویم، مرخصی، شیفت، قواعد | `T5CnnStr` | نصب‌کنندهٔ T5V3 |
| `Personnel` | پرسنل، واحد، عنوان شغلی، نوع استخدام، دستگاه | `PersonnelCnnStr` | نصب‌کنندهٔ T5V3 |
| `Link5 service database` | صف و لاگ سرویس دستگاه | — | سرویس دستگاه؛ **پورتال به آن وصل نمی‌شود** |

`engine/relations.json` این را ماشین‌خوان ثبت می‌کند: **۱۳۰ جدول**، تقسیم‌شده به `t5` = ۵۴،
`personnel` = ۳۳، `device` = ۴۰ و `portal` = ۳ (جدول‌های خودِ پورتال).

### چهار شاهد که «وفاداری» را اثبات می‌کند، نه ادعا

| شاهد | چه چیزی را ثابت می‌کند | آزمون/ابزار |
| :-- | :-- | :-- |
| `engine/engine-pin.json` | مدل، از بیلد قفل‌شدهٔ `T5Web [3.5.7]` خوانده می‌شود، نه از حدس | `verify-engine-pin.py` |
| `engine/column-types.json` | ۷۵ جدول / ۶۱۶ ستون با شاهد `ddl` یا `orm`؛ صفر ستون بی‌شاهد | `engine-column-types.py --check` |
| `db/verify.sql` | هر شیء و ستونی که کد به آن دست می‌زند، روی سرور واقعی موجود است | اجرا روی سرور |
| `db/03-relations.sql` | داده واقعاً رابطه‌هایی را که کد فرض می‌کند رعایت می‌کند | اجرا پیش و پس از هر انتقال |

### چیزی که پورتال اضافه می‌کند (و همین سه/یک جدول است)

`db/01-t5web-objects.sql` فقط سه جدول می‌سازد و **هیچ `ALTER` روی جدول‌های فروشنده ندارد**:

| جدول | کار | چرا لازم است |
| :-- | :-- | :-- |
| `T5WebAccess` | ماتریس دسترسی خود پورتال (قابلیت ← ممنوع/فقط‌خواندن/مجاز) | موتور مفهوم «سطح دسترسی وب» ندارد |
| `T5WebAudit` | دفتر رخداد فقط-افزودنی با زنجیرهٔ هش | پاسخ به «چه کسی چه چیزی را عوض کرد» |
| `T5WebDeviceCommand` | صف پایدار دستور دستگاه | نسخهٔ قدیم مستقیم HTTP به سرویس `Link5` می‌زد |

بازنویسی دیگر (`TWF`) هم همین سیاست را دارد و تنها یک جدول خودش را می‌سازد: `PassCheckProps`
(تاریخچهٔ تغییر کلمهٔ عبور). هیچ‌کدام جدول «سایه»، ویو یا ستون کمکی روی جدول‌های موتور نساخته‌اند؛
اگر ساخته بودند، ارتقای بعدی موتور آن‌ها را بی‌صدا حذف می‌کرد.

**پیامد عملی:** نسخهٔ دسکتاپ و پورتال می‌توانند هم‌زمان روی همان داده کار کنند (حالت `coexist`،
`docs/08` §۴). چیزی «دو نسخه‌ای» یا «همگام‌سازی» لازم نیست، چون داده یکی است.

### جاهایی که عمداً «هم‌شکل فرض» نشده

| مورد | وضعیت | دلیل |
| :-- | :-- | :-- |
| `EmpTypeLeave` | هیچ DDL ندارد | نوع ستون‌ها حدس زده نشد؛ ماژول ساخته نشد |
| `EditedValue` | نام ستون‌ها بین DDL و ORM یکی نیست | نوشتن روی حدس ممنوع؛ probe از DBA لازم است |
| `Template` (اثر انگشت/چهره) | فقط‌خواندنی نیست، ساخته نشد | نوشتنش کار خود دستگاه است |
| جدول‌های `device` | خارج از دامنهٔ پورتال | رشتهٔ اتصال دوم = سطح حملهٔ دوم |
| گزارش‌های محاسباتی (`T5V3.Attendance`، `LeaveCalcs`) | بازنویسی نشد | عدد رسمی باید از موتور بیاید |

## ۲. سناریو الف — نصب پورتال کنار نسخهٔ قدیم (حالت پیش‌فرض)

**داده جابه‌جا نمی‌شود.** این حالت ۹۵٪ نصب‌هاست.

| گام | کار | نتیجهٔ مورد انتظار |
| :-- | :-- | :-- |
| ۱ | `db/01-t5web-objects.sql` | «T5Web portal objects are in place» |
| ۲ | `db/02-t5web-sql-login.sql` | کاربر کم‌دسترسی ساخته/به‌روز شد |
| ۳ | `verify.sql` | هیچ سطر `MISSING` نباشد |
| ۴ | `T5WebMode = coexist` در `Web.config` | نوار زرد «حالت هم‌زیستی» بالای صفحه‌ها |
| ۵ | `/Diagnostics` | اتصال هر دو کاتالوگ سبز، شمارش جدول‌ها غیر `-1` |
| ۶ | ماتریس `/Access` | حداقل یک نفر `PortalAdmin`؛ بقیه طبق وظیفه |

**دو نکته که فراموش می‌شوند:**

* **چه کسی اجازهٔ ورود دارد؟** ستون `UserInfo.WebUser` در کاتالوگ `Personnel`. کسی که آن‌جا
  `WebUser = 0` است، حتی با مجوز کامل پورتال هم نمی‌تواند وارد شود. این ستون مال موتور است و
  پورتال آن را عوض نمی‌کند.
* **قاعدهٔ طلایی:** در حالت `coexist` هر رکورد را فقط در **یک** برنامه ویرایش کنید. هیچ قفلی روی
  رکورد نیست؛ دو ویرایش هم‌زمان، آخرین نوشته را برنده می‌کند.

## ۳. سناریو ب — جابه‌جایی سرور یا ادغام (انتقال واقعی)

اینجا داده جابه‌جا می‌شود، ولی اسکیما نه. بنابراین کار، «مهاجرت» نیست؛ **بازگردانی + اثبات** است.

### ۳-۱. پیش از هر چیز: اثر انگشت بگیرید

```bash
# روی سرور مبدأ، پیش از هر تغییر
python3 tools/migration-fingerprint.py --sql > source.sql
sqlcmd -S SOURCE -E -i source.sql -o source-before.txt -h -1 -W -s ""

# روی سرور مقصد، پس از بازگردانی
python3 tools/migration-fingerprint.py --sql > target.sql
sqlcmd -S TARGET -E -i target.sql -o target-after.txt -h -1 -W -s ""

python3 tools/migration-fingerprint.py --compare source-before.txt target-after.txt
```

اثر انگشت سه چیز را ثبت می‌کند: **تعداد سطر هر ۸۷ جدول** دو کاتالوگ، **seed هر جدول
IDENTITY**، و **collation/سازگاری/نسخهٔ SQL**. جدولی که در نصب قدیمی وجود ندارد، `MISSING`
گزارش می‌شود نه خطا — تا مبدأ و مقصد با یک معیار سنجیده شوند.

خروجی صفر خطا یعنی: هیچ سطری کم یا زیاد نشده، و هیچ کلیدی دوباره استفاده نمی‌شود.

> اگر فقط `identity` یا `collation` تفاوت داشت، ابزار به‌صورت پیش‌فرض **هشدار** می‌دهد و
> `--strict-identity` / `--strict-meta` آن را به خطا تبدیل می‌کند. برای پذیرش نهایی، سخت‌گیر باشید.

### ۳-۲. ترتیب عملیات (پنجرهٔ توقف)

| # | کار | چرا این ترتیب |
| :-- | :-- | :-- |
| ۱ | توقف نوشتن: سرویس دسکتاپ و پورتال را بخوابانید (Application Pool = Stop) | بدون توقف، دو کاتالوگ از دو لحظهٔ مختلف پشتیبان می‌شوند |
| ۲ | `BACKUP DATABASE [ReportT5V3]` و `[Personnel]` با `WITH COMPRESSION, INIT` | دو پشتیبان **در یک پنجره** |
| ۳ | اثر انگشت مبدأ (`source-before.txt`) | مرجع مقایسه |
| ۴ | `RESTORE` هر دو کاتالوگ روی مقصد، با `WITH MOVE` به مسیر داده‌های مقصد | اگر `MDF` را Attach کنید، مسیر فایل و مالکیت قدیمی می‌آید |
| ۵ | `db/01-t5web-objects.sql` روی مقصد | سه جدول پورتال (idempotent) |
| ۶ | `db/02-t5web-sql-login.sql` + نگاشت لاگین‌ها | کاربر SQL قدیمی به SID قدیمی وصل است و «یتیم» می‌شود (`ALTER USER ... WITH LOGIN`) |
| ۷ | اثر انگشت مقصد + `--compare` | اثبات بند ۳-۱ |
| ۸ | `db/03-relations.sql` | هیچ سطر `VIOLATION` نباشد |
| ۹ | `verify.sql` | هیچ `MISSING` نباشد |
| ۱۰ | پیکربندی برنامه‌ها: `T5CnnStr`/`PersonnelCnnStr` پورتال، تنظیمات اتصال T5V3 دسکتاپ، آدرس سرویس `Link5` | هر سه باید به **یک** سرور اشاره کنند |
| ۱۱ | اجرای پورتال، `/Diagnostics` سبز، سپس سرویس دسکتاپ | اول پورتال فقط-خواندنی، بعد نویسنده‌ها |

### ۳-۳. چیزهایی که در جابه‌جایی واقعاً می‌شکنند

| نشانه | علت | درمان |
| :-- | :-- | :-- |
| متن فارسی جست‌وجو نمی‌شود یا `ی`/`ي` فرق می‌کند | collation مقصد متفاوت است (`SQL_Latin1...` به‌جای `Persian_100_CI_AS`) | هر دو کاتالوگ را با همان collation مبدأ بازگردانید؛ و در اثر انگشت، خط `meta|collation` را برابر کنید |
| `Cannot insert duplicate key` بعد از انتقال | `IDENTITY` از ۱ شروع شده (ری‌استور دستی/INSERT دستی) | `DBCC CHECKIDENT('Table', RESEED, <max key>)` — و در اثر انگشت با `--strict-identity` بگیرید |
| گزارش «پرسنل ناموجود» پر می‌شود | یکی از دو کاتالوگ از لحظهٔ دیگری بازگردانده شده | هر دو را در همان پنجرهٔ توقف بازگردانید |
| ورود به پورتال ممکن است ولی هیچ منویی نیست | `T5WebAccess` روی مقصد خالی است (درست است) | ماتریس `/Access` را دوباره پر کنید |
| دستور دستگاه در صف می‌ماند | سرویس دسکتاپ به سرور قدیم وصل است | اتصال `Link5` را به مقصد تغییر دهید |
| `Personnel` روی سرور دیگری است | پرس‌وجوی بین‌کاتالوگی | پورتال همین را لازم دارد: هر دو روی **یک** نمونه؛ وگرنه نیمهٔ هر کاتالوگ را جدا اجرا کنید |

### ۳-۴. بازگشت (rollback)

۱. `T5WebMode = legacy` و ری‌استارت Application Pool (۳۰ ثانیه) — پورتال کنار می‌رود.
۲. اگر داده هم باید برگردد: `RESTORE` از پشتیبان بند ۲. توجه: این کار **نسخهٔ قدیم را هم** به همان
لحظه برمی‌گرداند، چون داده یکی است. پیش از بازگردانی از `/Audit` خروجی بگیرید.
۳. بازگشتی که روی سرور آزمایشی آزمون نشده باشد، بازگشت نیست.

## ۴. سناریو ج — ورود داده از یک سامانهٔ دیگر (Excel یا نرم‌افزار دیگر)

این حالت **کپی پایگاه‌داده نیست**؛ پایگاه‌دادهٔ مبدأ اسکیمای دیگری دارد. سه لایه دارد و
ترتیبشان اهمیت دارد:

### لایهٔ ۱ — دادهٔ پایه (باید اول باشد)

`Department` (درخت واحدها) ← `TitlesChart` (عنوان شغلی) ← `EmpType` ← `LeaveTypes` ←
`Gate`/`Device` (دستگاه‌های تردد). از مسیر `/Modules` در پورتال یا از نسخهٔ دسکتاپ، هر دو
همان جدول‌ها را می‌نویسند. **شناسه‌ها را خودتان تعیین نکنید** مگر آن‌که مطمئنید با ترتیب موتور
تصادم نمی‌کند؛ ماژول‌های کلیددار پورتال، شناسه را اپراتور می‌گیرند و تکرار را رد می‌کنند.

### لایهٔ ۲ — پرسنل

| راه | چه می‌کند | محدودیت |
| :-- | :-- | :-- |
| نسخهٔ دسکتاپ T5V3 | اضافه‌کردن نفر جدید | **تنها راه درست برای افزودن**؛ شمارهٔ کارت دستگاه و ترتیب شمارهٔ پرسنلی را موتور می‌سازد |
| `/Import` پورتال (CSV UTF-8) | **به‌روزرسانی** پرسنل موجود | افزودن نفر را عمداً رد می‌کند؛ اگر پورتال شمارهٔ کارت بسازد، دستگاه او را نمی‌شناسد |

قالب CSV پورتال: `badge,firstname,lastname,nationalno,phone,email,deptid,emptypeid,hireddate,fireddate`
(پیش‌نمایش پیش از نوشتن، اعتبارسنجی هر سلول، و شمارش «به‌روزرسانی/ناموفق»).

پس مسیر امن برای یک سازمان تازه: **نفرات را با نسخهٔ دسکتاپ (یا ابزار خود موتور) وارد کنید**،
سپس با CSV پورتال فیلدهای تماسی و سازمانی را به‌روز کنید.

### لایهٔ ۳ — تردد و مرخصی تاریخی

| داده | راه پیشنهادی | نکتهٔ ایمنی |
| :-- | :-- | :-- |
| تردد خام (`Record`) | جدول موقت (staging) → اعتبارسنجی → درج نهایی | کلید منطقی `(BadgeNumber, Date, Time)`؛ تکرار یعنی دو رکورد برای یک تردد |
| مرخصی (`LeavesAdded`/`DailyLeave`) | از نسخهٔ دسکتاپ یا staging با همان قواعد | مانده‌ها (`YearRemain`) باید با همان عملیات ساخته شوند، نه دستی |
| شیفت | `Schedule`/`ShiftDetail` از پورتال (`/Schedule`) | هم‌پوشانی بازه‌ها با گارد داخل تراکنش رد می‌شود |
| ماندهٔ سال | ابزار «انتقال مانده سال» پورتال | محافظ تکرار دارد؛ سطرهای انتقال با شرح مشخص ثبت می‌شوند |

**هرگز:** `MachineNumber` یا `UserID` را برای دستگاه از خودتان نسازید؛ دستگاه تردد را با
شناسه‌ای می‌فرستد که در پایگاه سرویس دستگاه معنا دارد.

### چه چیزی منتقل **نمی‌شود**

| مورد | چرا | جایگزین |
| :-- | :-- | :-- |
| الگوی اثر انگشت/چهره (`Template`) | دادهٔ دودویی مخصوص دستگاه | ثبت‌نام دوباره روی دستگاه |
| جدول‌های کاتالوگ `device` | خارج از دامنهٔ پورتال | همان سرویس دستگاه، بدون تغییر |
| زنجیرهٔ حسابرسی قدیم | `T5WebAudit` از امروز شروع می‌شود | خروجی CSV/PDF دفتر قدیم را به‌عنوان شاهد نگه دارید؛ تاریخ جعلی نسازید |
| ماتریس دسترسی | پورتال مفهوم تازه‌ای است | یک‌بار در `/Access` تعریف شود |
| گزارش‌های محاسباتی | عدد رسمی از موتور می‌آید | از نسخهٔ دسکتاپ یا قالب RDLC بگیرید |
