# ۰۲ — گزارش فازها (Phase Log)

این سند تاریخچه اجرای فازها را نگه می‌دارد: در هر فاز چه ساخته شد، چه عیبی پیدا شد،
چه آزمونی اضافه شد، و چه چیزی باقی ماند. **این سند گذشته است؛ وضعیت جاری در
`docs/phase-status.csv` و برنامه آینده در `docs/06-phase-plan.md` است.**

قاعده: هر سطر این سند باید یا به یک فایل موجود اشاره کند یا به یک آزمون با شناسه مشخص.
اگر چیزی ساخته شد و بعد حذف شد، سطرش می‌مانَد و دلیلش نوشته می‌شود — تاریخ را بازنویسی نمی‌کنیم.

## فاز ۱ — زیرساخت و امنیت ✅

| مورد | خروجی |
| :-- | :-- |
| احراز هویت | `Web.config`: `authentication mode="Windows"`, `deny users="?"`؛ تطبیق نام ویندوزی با `UserInfo.UserName` و شرط `WebUser = 1` |
| مجوزدهی | `T5Web.Domain/AdminFeature.cs` (۱۰ قابلیت)، `AccessLevel {Deny=0, ReadOnly=1, Allow=2}`، `T5Web.Web/Security/AdminAuthorize.cs` |
| ترکیب دسترسی | `AccessService`: «منع برنده است» (deny wins) در ادغام سطرهای دسترسی |
| حسابرسی | `AuditService`: زنجیره هش SHA-256، درج فقط، `db/01-t5web-objects.sql` |
| اسکریپت‌های DB | `db/01-t5web-objects.sql` (دو جدول اختصاصی)، `db/02-t5web-sql-login.sql` (کاربر کم‌دسترسی)، `db/verify.sql` |
| شروع امن | `MvcApplication`: خواندن `T5CnnStr`، ساخت مخزن، تبدیل خطای پیکربندی به صفحه فارسی |
| آزمون‌ها | `T01`…`T05`, `T11`, `T12` |

**تصمیم مهم:** ورود با رمز حذف شد. موتور هیچ متد احراز رمز عبور در `T5V3.DB` ندارد
(`PassCheck`/`PassCheckProps` در بیلد وجود ندارند) و ساختن یک جدول رمز موازی یعنی دو
منبع حقیقت برای هویت. احراز هویت به IIS/Negotiate سپرده شد و هویت ویندوزی با
`UserInfo.UserName` تطبیق داده می‌شود. کاربر برکنارشده (`FiredDate`) و کاربر غیروب
(`WebUser = 0`) رد می‌شوند.

## فاز ۲ — قواعد کاری ✅

| مورد | خروجی |
| :-- | :-- |
| چارت سازمانی | `DepartmentService.BuildTree` — یتیم‌ها به ریشه می‌چسبند (حذف نمی‌شوند)، عمق تخصیص می‌یابد، حلقه (والد خودش/نوه) رد می‌شود |
| اعتبارسنجی پرسنل | `PersonnelService`: شماره پرسنلی یکتا، نام اجباری، تاریخ استخدام ≤ پایان کار، کاربر برکنارشده غیرفعال |
| گردش کار | `WorkflowService`: تکرار عنوان، پذیرش توسط خود، شکاف در زنجیره، ترتیب صحیح |
| تاریخ شمسی | `PersonnelService.ToJalali` روی `PersianCalendar` |
| منو/قابلیت | `MenuService`-معادل در `AccessService`: قابلیت‌های قابل‌ویرایش از قابلیت‌های فقط‌خواندنی جدا می‌شوند |
| آزمون‌ها | `T01`…`T07` |

**تصمیم مهم:** فرض «هر کسی که در `UserInfo` هست، کاربر وب است» حذف شد. دسترسی وب با
`WebUser = 1` + سطر در `[T5WebAccess]` تعیین می‌شود، چون کاربر گفته بود
«قرار نیست همه به T5Web دسترسی داشته باشن».

## فاز ۳ — لایه داده و آداپتر موتور ✅

| مورد | خروجی |
| :-- | :-- |
| نقشه اسکیما | `T5Web.Data/SchemaMap.cs` — تنها منبع نام جدول/ستون در SQL پورتال |
| مخزن SQL | `SqlAdminRepository.cs` (Dapper، همگام) |
| دایرکتوری موتور | `T5Web.Data/Engine/PersonnelEngineDirectory.cs` + `IEngineDirectory.cs` + `EngineAccessException.cs` |
| قرارداد مدل موتور | `tools/engine-model-contract.py` → `engine/model-contract.json` (۴ نوع، ۳۹ عضو) |
| مخزن آزمون | `InMemoryAdminRepository.cs` — همان قرارداد، بدون SQL |
| گیت بیلد | `build-and-test.sh` گام پنجم: `engine-model-contract.py --check` |
| آزمون‌ها | `T08` (انطباق SQL)، `T14` (قرارداد موتور) |

**چرا این فاز مهم‌ترین فاز بود:** در فاز ۱ چهار موجودیت با SQL دست‌ساز خوانده می‌شد و همان‌جا
هفت شناسه ناموجود پیدا شد (`BUG-01`…`BUG-07`). از این فاز، خواندن ساختار سازمانی از
`Personnel.DB.DepartmentDA`/`TitleChartDA`/`EmpTypeDA`/`DeviceDA` انجام می‌شود، پس دیگر
اسکیمای موتور در دو جا نگه‌داری نمی‌شود.

**چرا نوشتن به موتور سپرده نشد:** `AddNew/Edit/Delete` موتور به `DBManager` نمونه-سراسری
وابسته‌اند و متد `UpdateDB` در مهندسی ۳.۹.۲ حذف شده است (ناسازگاری مستندشده در
`../TWF/docs/03-engine-compatibility-verdict.md`). اشتراک آن در فرایند وب یعنی وابستگی
پورتال به وضعیت دسکتاپ. پس نوشتن در SQL می‌مانَد، ولی با `SchemaMap` و با گیت
`verify-sql-schema.py`.
