# مسیر .NET 10 بدون خرابی — همان کاری که انجام شد، و آنچه هنوز مانده

**سؤال:** «چطور می‌تونی بازنویسی کدها را به .NET 10 ببری، بدون خرابی و مشکل؟»

**پاسخ کوتاه:** با «مهاجرت یک‌جا» نه. با چهار مرحله‌ای که هر کدام جداگانه اثبات
می‌شود، و هیچ مرحله‌ای شروع نمی‌شود تا مرحلهٔ قبلی با کامپایلر و تست سبز باشد.
مرحلهٔ ۱ **انجام و اثبات شد** (کدِ اجراشده در `fcc2a9f`/`c56e0ef` و run
`40332868890`). مراحل ۲ تا ۴ طراحی‌شده‌اند و با «قفل رشد» در CI نگه داشته می‌شوند.

این سند مکمل `docs/16-net8-feasibility.md` است: آن سند اندازه‌گیری کرد «چقدر دوریم»،
این سند مسیرِ رسیدن و کنترلِ «خراب نشدن» را می‌دهد.

---

## ۰. چرا .NET 10 و نه صرفاً .NET 8

- **.NET 10 = LTS** (انتشار نوامبر ۲۰۲۵، پشتیبانی سه‌ساله). .NET 8 هم LTS است و تا
  نوامبر ۲۰۲۶ پشتیبانی می‌شود؛ یعنی اگر امروز فقط به ۸ برویم، چند ماه بعد دوباره یک
  مهاجرت کامل لازم است. پرشِ مستقیم به ۱۰ منطقی‌تر است، **به شرطی** که لایهٔ پایین روی
  هر دو کامپایل شود — که همین حالا می‌شود.
- هزینهٔ .NET 8 و .NET 10 برای این کد یکسان است: هر دو ASP.NET Core می‌خواهند و
  `System.Web` در هیچ‌کدام نیست. تفاوت عملاً در نسخهٔ بسته‌ها و چند API است، نه در مسیر.
- بنا بر این spike از این پس **دو هدف** دارد: `net8.0` و `net10.0`. اگر روزی کدی روی
  ۸ کامپایل شد و روی ۱۰ نشد، همان diff دقیقاً جوابِ «چقدر مانده» است.

## ۱. مرحلهٔ ۱ — برداشتن قفل پلتفرم (انجام شد ✅)

قفلِ واقعی، اسمبلی موتور بود: `Personnel.dll` یک اسمبلی **.NET Framework، x86، EF6**
است. تا وقتی حتی یک فایلِ لایهٔ داده آن را لود می‌کرد، سه چیز همیشه همراه آن بود:

1. app pool **۳۲-بیتی** (`enable32Bit=True`) — و روی IIS 10 یعنی محدودیت حافظه و
   ناسازگاری با هر ابزار مدرن؛
2. پوشهٔ موتور روی وب‌سرور + پین‌شدن نسخه؛
3. خودِ **.NET Framework**، که در .NET 10 وجود ندارد.

### کاری که انجام شد

| فایل | نقش |
| :-- | :-- |
| `T5Web.Data/Engine/SqlEngineDirectory.cs` (تازه) | همان چهار خواندن — `Department`, `TitlesChart`, `EmpType`, `Device` — با Dapper و SQL، روی **همان** کارخانهٔ اتصالِ Personnel |
| `T5Web.Data/Engine/EngineDirectory.cs` (تازه) | انتخابِ خواننده از `T5WebEngineDirectory`: `sql` (پیش‌فرض) / `engine` / `auto` |
| `T5Web.Web/Web.config` | کلید تازه با مقدار پیش‌فرض `sql` |
| `T5Web.Tests/Program.cs` — T44 (تازه) | قفلِ رفتاری: پیش‌فرض `sql`، `engine` هنوز موجود، و **هیچ فایل دیگری** حق وابستگی به موتور ندارد |

سه نکتهٔ طراحی که عمدی است، چون همان‌ها تفاوت «مهاجرت بی‌خطر» و «مهاجرت شجاعانه» است:

1. **ستون‌ها حدس نیستند.** از `engine/column-types.json` (که از مدل خود موتور + DDL
   ساخته شده) گرفته شده‌اند و علاوه بر آن، هر چهار `SELECT` در job دیتابیس مقابل یک
   **SQL Server واقعی** با `SET NOEXEC ON` کامپایل می‌شوند (`tools/sql-smoke.py`), یعنی
   هر ستون و هر نام جدول در موتور حل می‌شود. متنِ صرفاً درست کافی نیست.
2. **`COALESCE(NULLIF([Name], N''), [DepartmentName], N'')`** — جدول هم `Name` دارد هم
   `DepartmentName`؛ اگر فقط یکی پر باشد، فهرستِ خالی «خرابی» است، نه خطا.
3. **`SqlEngineDirectory` هیچ نامی از موتور نمی‌برد و `EngineDirectory` هیچ نامی از
   `SqlConnection`.** هر دو خواننده به‌صورت *factory* پاس داده می‌شوند. اگر این کار را
   نمی‌کردم، همان فایلِ انتخاب‌کننده هم روی .NET 10 کامپایل نمی‌شد و «قفل» فقط یک
   فایل جابه‌جا می‌شد.

### اثبات (اجراشده، نه ادعا)

```
NET8 coupling | core files 51 | engine-coupled 1 | System.Web 0 | System.Configuration 0
net8.0  build | errors 0 | warnings 0
net10.0 build | errors 0 | warnings 0
```

و در همان run (`40332868890`) هر چهار job سبز: `MSBuild + tests` (۴۴ تست، شامل T44)،
`SQL Server scripts` (شامل کامپایل چهار `SELECT` تازه)، `IIS + the published console`،
`Portability`.

**معنای دقیق این اعداد:** «لایهٔ داده و منطقِ این برنامه روی .NET 10 کامپایل می‌شود و
روی .NET Framework هم همان تست‌ها را پاس می‌کند». معنایش این **نیست** که برنامه روی
.NET 10 اجرا شده؛ هنوز یک صفحه، یک route، یک مسیر احراز هویت روی .NET 10 اجرا نشده
است. آن کار مرحلهٔ ۲ و ۳ است.

## ۲. مرحلهٔ ۲ — لایهٔ وب: شِمارش، بعد تصمیم (قفلش گذاشته شد ✅)

لایهٔ وب همان چیزی است که `.NET 10` را از یک «تنظیم» به یک «پورت» تبدیل می‌کند، چون
`System.Web.Mvc` در ASP.NET Core **وجود ندارد**. اندازه‌گیری امروز:

| مورد | تعداد | در ASP.NET Core |
| :-- | --: | :-- |
| فایل‌های `T5Web.Web` | ۲۷ | — |
| فایل‌هایی که `System.Web` دارند | **۲۳** | `Microsoft.AspNetCore.Mvc` |
| کنترلرها | ۲۲ | همان کلاس‌ها، امضای متفاوت |
| Viewها | ۳۴ | تقریباً بدون تغییر (فقط `@inherits`/`@model`) |
| `HttpContext.Current` | **۲** (هر دو در `AdminAuthorize.cs`) | `IHttpContextAccessor` |
| `ConfigurationManager` | **۴ فایل** | `IConfiguration` |
| `ActionResult` | ۶۴ | `IActionResult` |
| `ViewBag.*` | ۵۶ | `ViewData` (کامپایل می‌شود، ولی بی‌نوع) |
| `[ValidateAntiForgeryToken]` | ۱۸ | تغییر نام به `AutoValidateAntiforgeryToken` |
| نقاط کوپلینگ (جمع) | **۲۵۰** | — |

از امروز این عدد **قفل** است: `tools/web-port-budget.py --check` در CI اجرا می‌شود و
اگر هر شمارنده‌ای *بزرگ‌تر* شود، job قرمز می‌شود:

```
::notice::WEB PORT | webFiles 27 | System.Web 23 | controllers 22 | views 34 |
          HttpContext.Current 2 | ConfigManager 4 | coupling points 250
```

این «قفل رشد» مهم‌ترین بخش این مرحله است. شکستِ واقعیِ پورت‌ها همیشه کامپایل‌نشدن
نیست؛ این است که کدِ تازه کنارِ کدِ پورت‌شده `System.Web` بردارد و روز حذف اسمبلی،
دوباره همه‌چیز به هم وصل شود. با این ابزار، فاصله فقط کم می‌شود و هر کاهش با یک
کامیتِ صریح ثبت می‌شود (`--write` فقط وقتی مجاز است که پورت انجام شده باشد).

## ۳. مرحلهٔ ۳ — پورتِ وب به ASP.NET Core، برش‌به‌برش

قاعدهٔ اصلی: **یک برش = یک صفحه/مسیر که هم قبل و هم بعد رفتار یکسان دارد، با تست.**
هیچ برشی «فقط کامپایل شود» پذیرفته نیست، چون کامپایل‌شدن همان چیزی است که
«بی‌خطر» را قاطی می‌کند با «آخرین بار کار می‌کرد».

### ۳.۱ ترتیب برش‌ها (چرا این ترتیب)

| # | برش | چرا اول/آخر | ریسک |
| --: | :-- | :-- | :-- |
| ۰ | پروژهٔ `net10.0` برای `Domain`+`Application`+`Data` | صفر ریسک؛ همین حالا هست (`spike/net8`) | — |
| ۱ | `Security/AdminAuthorize.cs` + `Coexistence` + `ModuleSwitch` | **احراز هویت و مجوز اولین چیز است، نه آخرین.** بعد از پورت، تست‌های دسترسیِ موجود باید بدون تغییر پاس شوند | **بالا** |
| ۲ | `MvcApplication.cs` → `Program.cs` (DI، routing، فیلترها، خطاها) | تعیین‌کنندهٔ «شکل» اجرا؛ تا این نباشد بقیه اجرا نمی‌شوند | متوسط |
| ۳ | `AccountController` + `HomeController` + `Dashboard` | کوچک‌ترین مسیر کامل «ورود تا صفحه» برای اثبات قالب | متوسط |
| ۴ | بقیهٔ کنترلرها، یکی‌یکی، به ترتیبdependency | هر کنترلر یک کامیت + یک تست | پایین |
| ۵ | Viewها (`@model`/`@inherits`، helperهای `Html.*` که در Core تغییر نام داده‌اند) | تقریباً مکانیکی | پایین |
| ۶ | `T41` (پارسِ Razor با `System.Web.Razor`) | این تست در Core **نمی‌ماند**؛ جایگزین: کامپایل Viewها در `dotnet build` (Razor SDK خودش این کار را می‌کند، یعنی تست به سطح پایین‌تری منتقل می‌شود) | متوسط |

### ۳.۲ شِیم یا بازنویسی؟

دو راه، و انتخاب باید صریح باشد:

- **شِیم (`System.Web.Mvc` سازگاری)**: سریع، ولی یک وابستگی تازه می‌سازد که فقط
  «درد را عقب می‌اندازد» و با `net10.0` روی IIS هیچ پشتیبانی رسمی ندارد. **رد شد.**
- **بازنویسی سطحی (انتخاب‌شده)**: همان کلاس‌ها و همان نامِ Actionها، با
  `Microsoft.AspNetCore.Mvc`؛ `ActionResult` → `IActionResult`؛ `ViewBag.X` → `ViewData["X"]`
  (یا بهتر: مدل‌های typed که ۵۶ موردِ `ViewBag` را کم می‌کند)؛ `HttpContext.Current` →
  تزریقِ `IHttpContextAccessor`؛ `ConfigurationManager` → `IConfiguration`؛
  `[ValidateAntiForgeryToken]` → `AutoValidateAntiforgeryToken` (یک attribute سراسری،
  یعنی ۱۸ مورد به ۱ مورد تبدیل می‌شود — و همان ۱ مورد امن‌تر از امروز است).
- **Viewها**: ۳۴ فایل، عمدتاً بی‌تغییر. `@Html.Partial` → `@await Html.PartialAsync` و
  مانند آن، مکانیکی و قابل‌شمارش.

### ۳.۳ هارنسِ برابری (چیزی که «بدون خرابی» را قابل‌اثبات می‌کند)

قبل از پورت، یک هارنس بسازیم که **خروجیِ HTML** هر مسیر را در نسخهٔ Framework ثبت کند
(با یک دیتابیس نمونهٔ ثابت) و بعد از هر برش، همان مسیر را در Core بگیرد و diff کند.
تست‌های موجود (۴۴ مورد) منطق را می‌پوشانند، ولی «صفحه درست است» را نه.

- فیکسچر: `tools/synthetic-schema.py` (همین حالا در CI اجرا می‌شود) + ردیف‌های نمونهٔ
  ثابت.
- ثبت: برای هر مسیر، کد وضعیت + هدرهای مهم + بدنهٔ نرمال‌شده (حذف timestamp/anti-forgery).
- معیار قبولی: diff = ۰ برای مسیرهای «بی‌تغییر»؛ هر تفاوت باید در همان کامیت توضیح داده
  شود و گرنه برش رد است.

این هارنس هنوز ساخته نشده — و صادقانه: **تا ساخته نشود، پورت وب شروع نمی‌شود.**

## ۴. مرحلهٔ ۴ — بسته‌بندی و استقرار

- `web.config` فعلی (System.Web) با `appsettings.json` + `web.config` مینیمال برای IIS
  جایگزین می‌شود؛ کلید `T5WebEngineDirectory` و بقیهٔ کلیدها منتقل می‌شوند
  (`docs/08` به‌روز می‌شود).
- **ASP.NET Core Module v2** روی IIS لازم است (`docs/13` — نصب‌ها از قبل مجاز است).
- app pool از `v4.0` + ۳۲-بیتی به **`No Managed Code` + ۶۴-بیتی** می‌رود؛ این همان
  سودی است که مرحلهٔ ۱ خرید.
- دو برنامه (کنسول T5Web و TWF) جدا می‌مانند؛ هیچ‌کدام به دیگری لینک نمی‌شود.

## ۶. ریسک‌هایی که باید صریح گفته شوند

1. **`AdminAuthorize.cs` (۵۲۷ خط) ریسکِ اصلی است.** پورتِ اشتباه آن یعنی «همه‌چیز کار
   می‌کند، فقط بعضی‌ها بیشتر از حقشان می‌بینند» — بدترین نوع خرابی، چون تستِ عملکردی
   نمی‌گیرد. قبل از پورتِ آن، ماتریسِ دسترسی (نقش × مسیر) باید به تست تبدیل شود.
2. **`T41` در Core معنا ندارد** (پارسِ Razor با `System.Web.Razor`). جایگزینش کامپایلِ
   View در build است؛ این یک تست را حذف و یک تضمین را اضافه می‌کند، ولی باید ثبت شود.
3. **تستِ ۴۴ موردی روی .NET Framework اجرا می‌شود، نه Core.** تا وقتی خودِ تست‌ها روی
   `net10.0` هم اجرا نشوند، «کدِ پورت‌شده درست است» فقط تا حد کامپایل اثبات شده.
4. **SQL Server 2016** به‌عنوان کفِ نسخه هنوز اثبات نشده (فقط ۲۰۲۵ موجود است).
   مهاجرت به Core این را بدتر نمی‌کند، ولی حلش هم نمی‌کند.
5. **زمانِ قطعی:** پورتِ وب یک کار چند-هفته‌ای است (۲۷ فایل، ۲۲ کنترلر، ۵۲۷ خط مجوز)،
   نه یک بعدازظهر. هر ادعای خلاف این، ادعایی است که در روز استقرار پرداخت می‌شود.

## ۷. توصیه

1. **امروز:** مرحلهٔ ۱ را در محیط واقعی مستقر کن (با `T5WebEngineDirectory=sql`). این
   تنها تغییری است که همین حالا ارزش دارد و ریسکش با تست پوشیده شده: app pool از
   ۳۲-بیتی آزاد می‌شود و `Personnel.dll` از مسیر اجرا حذف می‌شود.
2. **بعد:** هارنسِ برابری را بساز، بعد `AdminAuthorize` را پورت کن (با تستِ ماتریسِ
   دسترسی، قبل از پورت).
3. **بعد:** `Program.cs`، بعد کنترلرها یکی‌یکی؛ با هر برش، budget را پایین بیاور.
4. **.NET 10 را فقط وقتی اعلام کن که** `dotnet build` روی `net10.0` **و** تست‌ها روی
   `net10.0` **و** هارنسِ برابری سبز باشند. تا آن روز، جملهٔ درست این است:
   «لایهٔ داده و منطق روی .NET 10 کامپایل می‌شود؛ لایهٔ وب هنوز روی .NET Framework است.»
