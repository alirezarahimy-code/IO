# فاز ۳: طرح اسکیما و عملیات ایمن

**تاریخ:** ۲۰۲۶-۱۱-۰۸ — **وضعیت:** بنیاد آزمایشی نسخه‌دار؛ طراحی نهایی محصول و تصمیم‌های سازمان/مجوز هنوز بسته نشده‌اند. این سند طرح اولیه است، نه اجازهٔ استقرار. مدل و migration منبع دقیق نام، نوع و قیدهای اجرایی‌اند: `src/IO.Infrastructure/Storage/IoDbContext.cs`، `FoundationRecords.cs` و `Migrations/20261108225421_InitialFoundation.cs`.

## محدوده و روابط اجرایی

این migration فقط ۱۴ جدول زیر را می‌سازد، نه کل جدول‌های پیشنهادی مانیفست. کلید اصلی بیشتر جدول‌ها GUID و کلید جدول‌های واسط ترکیبی است؛ رابطه‌های صریح با حذف محدودکننده (`RESTRICT`/`NO ACTION`) تعریف شده‌اند. واحد و کارمند زیر یک شرکت هستند؛ این **فرض موقت D10** است و پیش از کاربرد عملی باید با مالک حوزه تأیید شود.

| حوزه | جدول‌ها | روابط و محدودیت مهم |
|---|---|---|
| سازمان | `Organizations`, `Companies`, `Sites`, `OrgUnits` | شرکت به سازمان، سایت و واحد به شرکت؛ والد واحد باید در همان شرکت باشد؛ خودوالدی ممنوع ولی چرخهٔ چندگرهی هنوز کنترل نشده است. منطقهٔ زمانی سایت فقط رشته است و اعتبار آن بررسی نشده. |
| کارمند | `Employees`, `EmployeeAssignments` | شمارهٔ پرسنلی در شرکت یکتاست؛ انتساب به کارمند و واحد **همان شرکت** وصل است و پایان باید بعد از شروع باشد. تاریخ پایان در مدل نیمه‌باز است. جلوگیری از هم‌پوشانی در دیتابیس هنوز وجود ندارد. |
| هویت و دسترسی | `Users`, `Roles`, `Permissions`, `UserRoles`, `RolePermissions`, `UserOrgScopes` | نام کاربری، نام نقش و کلید مجوز یکتا؛ جدول‌های واسط دارای کلید ترکیبی یکتا هستند؛ محدوده به کاربر و واحد FK دارد اما یکتایی یا منع هم‌پوشانی ندارد. حساب می‌تواند به کارمند وصل شود ولی یکتایی این اتصال تضمین نشده است. سیاست تفسیر محدوده، احراز هویت و کنترل دسترسی **اجرا نشده‌اند**. |
| رویداد خام | `EventSources`, `RawAttendanceEvents` | منبع به سایت وصل است؛ هر رویداد به منبع موجود وصل است و payload باینری، زمان دریافت UTC و فیلدهای اختیاری را نگه می‌دارد. `OccurredAtUtc` می‌تواند نامعلوم باشد. |

موجودیت‌های قابل ویرایش اصلی سازمان، کارمند و کاربر `rowversion` دارند؛ این پوشش کل جداول، تاریخچهٔ کامل یا حسابرسی نیست. تغییرات باید با کنترل هم‌زمانی مناسب توسط قابلیت‌های فازهای بعد اعمال شوند.

## قواعد رویداد خام

- `ExternalEventId` اختیاری و حداکثر ۱۸۰ واحد UTF-16 است. رشتهٔ خالی در SQL رد می‌شود؛ domain ورودی فقط شامل فاصله را نیز رد می‌کند ولی SQL به‌تنهایی این قاعده را تضمین نمی‌کند. فضا و حروف تغییر داده نمی‌شوند. مقدار `null` تکرارپذیر است؛ حذف حدسی تکراری‌های بدون شناسه ممنوع است.
- شاخص یکتای فیلترشده `(SourceId, ExternalEventIdBytes, ExternalEventIdByteLength)` با محاسبهٔ بایت‌های `nvarchar` و `DATALENGTH`، تفاوت حروف، فاصلهٔ انتهایی و NUL انتهایی را حفظ می‌کند؛ طول برای جلوگیری از اثر padding مقایسهٔ باینری SQL لازم است. هم‌زمانی درج شناسهٔ یکسان آزموده شده است. تفاوت بایت payload با شناسهٔ یکسان و سیاست گزارش/قرنطینهٔ برخورد هنوز پیاده نشده است.
- زمان‌های موجود `datetimeoffset` با offset صفر در SQL کنترل می‌شوند؛ این الزام به معنی تشخیص صحت ساعت دستگاه یا تبدیل محلی به UTC نیست. نگهداری منطقهٔ زمانی منبع اختیاری است و ابهام ساعت محلی/تغییر ساعت در مراحل بعد باید حل شود.
- trigger `TR_RawAttendanceEvents_Immutable` عملیات معمول `UPDATE` و `DELETE` روی ردیف موجود را رد می‌کند. این جایگزین مجوز محدود نیست: صاحب/مدیر دیتابیس می‌تواند trigger را غیرفعال کند، جدول را تغییر دهد یا `TRUNCATE` کند. طراحی حساب‌های سرویس، منع این مجوزها، حسابرسی، نگهداری/آرشیو و بازیابی هنوز لازم است. در migration بازگشتی حذف خود جدول عمداً ممکن است.
- payload ممکن است دادهٔ شخصی یا حساس داشته باشد؛ در CI فقط دادهٔ ساختگی استفاده می‌شود. حد حجم، رمزگذاری، retention و دسترسی به payload هنوز سیاست مصوب ندارند.

## تولید و بررسی migration به‌شکل ایمن

۱. به ریشهٔ `ReCode` بروید؛ Linux و SDK مطابق `global.json`، دسترسی به NuGet رسمی و ابزار `dotnet-ef` نسخهٔ ۱۰.۰.۱۱ لازم است. فقط روی محیط مجاز و بدون دادهٔ واقعی تمرین کنید. تست CI خودکار هنگام `push` روی شاخهٔ جلسه اجرا می‌شود.
۲. `./tools/phase02-verify.sh` build و آزمون domain را اجرا می‌کند، نه SQL. تست SQL حاضر عمداً فقط داخل GitHub Actions، روی loopback و با تأیید `IO_SQL_DISPOSABLE_TEST=yes`، رمز تصادفی و نام دیتابیس تصادفی اجرا می‌شود؛ راه آزمون محلی عمومی/تولیدی فراهم نکرده‌ایم. workflow کانتینر Developer موقت را حذف می‌کند و تست در `finally` دیتابیس خود را حذف می‌کند.
۳. برای **فقط تولید اسکریپت آفلاین** (بدون اتصال):

```bash
cd ReCode
dotnet tool install dotnet-ef --tool-path "$HOME/.dotnet/tools-io" --version 10.0.11
dotnet build IO.slnx --configuration Release
"$HOME/.dotnet/tools-io/dotnet-ef" migrations script 0 --idempotent \
  --project src/IO.Infrastructure --startup-project src/IO.Infrastructure \
  --configuration Release --no-build --output /tmp/io-foundation-review.sql
```

اگر ابزار قبلاً نصب است نسخهٔ آن را بررسی/به‌روزرسانی کنید؛ فایل SQL را بازبینی کنید و برای کاربرد واقعی جداگانه مدیریت کنید. `IoDbContextFactory` عمداً فقط connection string ثابت و غیرعملی `IO_DesignOnly` دارد؛ آن را به‌عنوان تنظیمات runtime یا مقصد اعمال migration تصور نکنید. اتصال عملی و مدیریت محرمانه‌ها در فازهای بعدی طراحی می‌شود.
۴. هر اعمال واقعی نیازمند مقصد صریح و مجاز، حساب محدود، برنامهٔ تغییر، بازبینی اسکریپت، backup و **آزمون بازیابی**، مانیتورینگ و طرح بازگشت است. هیچ رمز یا connection string واقعی در Git/خط فرمان/لاگ وارد نشود. SQL تست از گواهی خودامضا با `TrustServerCertificate=True` استفاده می‌کند؛ الگوی TLS تولید نیست.
۵. `Down` جدول‌ها و داده‌ها را حذف می‌کند. آزمون rollback فعلی تنها در دیتابیس مصنوعی disposable انجام می‌شود؛ آن را راه بازگشت امن محیط دارای داده قلمداد نکنید. برای هر migration آتی آزمایش ارتقا، تطبیق مدل و طرح بازیابی مستقل لازم است.

## بدهی‌ها و مرز پذیرش

D09 (دامنه و تفسیر مجوز، جانشینی و ساخت امن مدیر) و D10 (ساختار شرکت/کارمند، تاریخچه و انتساب) باز هستند؛ مدل فعلی پاسخ نهایی آن‌ها نیست. تعیین حساب‌ها و مجوزهای SQL، چرخه‌های واحد، هم‌پوشانی هم‌زمان انتساب‌ها، تاریخچه و audit، کلیدهای جایگزین/normalization با collation مورد توافق، و سیاست ذخیرهٔ داده‌های حساس باید پیش از استفادهٔ واقعی تکمیل شوند. هیچ پنل، API عملیاتی، احراز هویت، پردازش تردد یا اتصال به دستگاه ساخته نشده است. بدهی تحلیل اتمی ۱٬۲۲۲ خط و شواهد سامانه‌های قدیم همچنان باز است.
