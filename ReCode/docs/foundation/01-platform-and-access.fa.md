# پایهٔ بخش ۱ — اجرا، نقش و راهنما

## محیط هدف این برش
هسته C# / .NET 10 است. ماتریس CI: Windows Server 2022 x64 و Ubuntu 24.04 x64. ساخت، آزمون دامنه و کاتالوگ/راهنما، publish وابسته به runtime برای وب و bootstrap و اجرای `/health/live` از DLL منتشرشده روی هر سیستم انجام می‌شود. این smoke در حالت foundation-only و بدون دیتابیس است؛ اثبات نصب production، Windows Service/systemd، TLS، SQL روی Windows یا SDK دستگاه نیست. آزمون SQL/HTTPS/مرورگر در workflow جدا روی SQL Server Developer ایزولهٔ Linux انجام می‌شود.

SDK طبق `global.json` از خانوادهٔ .NET 10 پایدار است؛ `Directory.Build.props` هدف `net10.0` را تعیین می‌کند. در پوشهٔ `ReCode` با PowerShell 7 اجرا کنید:

```powershell
./tools/verify-platform.ps1
```

این فرمان فقط دادهٔ موقت انتشار می‌سازد، هیچ DB یا کاربر واقعی ایجاد نمی‌کند و فرایند smoke را در پایان می‌بندد. پوشهٔ موقت پاک می‌شود. وجود SDK، دسترسی به بسته‌های NuGet و پورت آزاد 5198 لازم است. در این سند هیچ رمز، کلید یا اتصال واقعی ذخیره نشده است.

## اجرا با دیتابیس مجاز
برنامه به‌صورت پیش‌فرض foundation-only است. فعال‌کردن `IO__EnableExperimentalIdentity=true` به اتصال صریح `ConnectionStrings__IO` و دیتابیس مجاز با دو مجموعهٔ migration نیاز دارد. از اجرای تست تخریبی SQL روی دادهٔ سازمان خودداری کنید؛ harness تست فعلی فقط GitHub Actions و DB تصادفی روی SQL موقت CI را قبول می‌کند.

ورود نیازمند HTTPS است؛ cookieهای Secure و بررسی CSRF عمداً برای راحتی نصب غیرفعال نشده‌اند. هیچ forwarded header خودکار قابل اعتماد نشده است. تنظیم سرویس، TLS، حفاظت/ماندگاری کلیدهای Data Protection، backup و نسخهٔ نصب واقعی هر دو سیستم در S28–S30 تکمیل می‌شود. اجرای بخش اول جای آن دروازه‌ها را نمی‌گیرد.

## محدودیت دستگاه
در این برش هیچ COM/DLL یا SDK قدیمی به پروژه لینک نشده است. هسته نباید برای اجرا به Windows وابسته شود. مدل/پروتکل/معماری SDK در S01 ثبت می‌شود. اگر یک مدل فقط از واسط Windows پشتیبانی کند، وابستگی باید پیش از انتخاب راهکار صریحاً اعلام و تأیید شود؛ آن را اجرای مستقل Linux معرفی نمی‌کنیم.

## نقش و دسترسی
- کاتالوگ واحد: `PermissionCatalog.All`. صفحهٔ نقش‌ها کدها و توضیح را از `/workspace/permission-catalog` می‌گیرد، نه آرایهٔ مستقل JavaScript.
- ۷۳ کد قابل اعطا/لغو؛ ۶۴ نگاشت عمل به مجوز ریز و بستهٔ قدیمی جایگزین. گروه‌هایی مانند مشاهدهٔ سازمان، ایجاد/تغییر پرسنل، تقویم، تردد خام/نگاشت/تعارض، محاسبه، دفتر مرخصی، تنظیمات و هویت تفکیک شده‌اند. این به معنی ساخت عملیات حذف یا قابلیت غایب نیست؛ عملیات غیرموجود مجوز خیالی نمی‌گیرد.
- مجوزهای قبلی حذف یا بی‌اجازه مهاجرت داده نشده‌اند. `identity.manage` و دیگر بسته‌های قدیمی همچنان مجوزهای گسترده‌اند؛ اگر بستهٔ قدیمی باقی باشد، لغو مجوز ریز به‌تنهایی عمل را ممنوع نمی‌کند. برای حداقل دسترسی، ابتدا مجوزهای ریز لازم را اعطا و سپس بستهٔ قدیمی را با حساب مدیریتی مستقل لغو کنید. محدودیت عدم لغو نقش/مسیر مدیریت خود همچنان برقرار است.
- کد مجوز دقیق و ordinal است؛ تغییر حروف و فاصله در سرور معتبر نمی‌شود. اجازهٔ داده/نوشتن در همان تراکنش عملیات بررسی می‌شود؛ منو و فرم تنها نمایش کمکی‌اند.
- جمع نقش‌ها مؤثر است؛ این برش «deny مستقیم کاربر» اضافه نمی‌کند. برای لغو واقعی، تمام مسیرهای اعطای آن حق را بررسی کنید.
- `/workspace/capabilities` فهرست منو را بر اساس دسترسی جاری می‌سازد. مدیر ارشد پنل مستقل دارد. اپراتورِ دارای قالب، پنل اطلاع‌رسانی می‌بیند ولی هنوز هیچ عملیات دستگاهی ندارد. محدودهٔ داده همچنان توسط سرویس مربوط بررسی می‌شود؛ داشتن پیوند، مجوز سراسری نیست.
- منو/فرم/راهنما هنگام بازگشت تمرکز یا هر ۳۰ ثانیه تازه‌سازی می‌شوند؛ خود API در درخواست بعدی دسترسی را دوباره کنترل می‌کند. «فوری در API» با push فوری تغییر منو یکسان نیست.

### ایجاد نقش‌های پایه
با حساب دارای `identity.manage` یا حق لازم مدیریت نقش به `/workspace/roles` بروید؛ مشاهدهٔ فهرست نیز مجوز `identity.roles.read` یا بستهٔ قبلی را لازم دارد. دکمهٔ «ایجاد نقش‌های پایهٔ غایب» را بزنید.

کارمند، مدیر واحد، مدیریت سامانه، مدیر ارشد و اپراتور با شناسه‌های ثابت ساخته می‌شوند. هیچ نقشی خودکار به حساب‌ها داده نمی‌شود. مدیر واحد برای ابزارهای شخصی باید نقش کارمند هم بگیرد و برای مشاهده/تصمیم دامنهٔ معتبر نیاز دارد. اپراتور فعلاً بدون مجوز عملیاتی دستگاه ساخته می‌شود.

اجرای دوباره، نقش و مجوز موجود را بازنویسی یا مجوز لغوشده را احیا نمی‌کند. اگر نام نقش پایه قبلاً با شناسهٔ سفارشی استفاده شده باشد، عملیات با تعارض متوقف می‌شود تا مدیر آگاهانه تعیین تکلیف کند. ایجاد نقش‌ها، اعطا/لغو و عملیات داده آدیت می‌شوند.

## راهنمای داخل سامانه
مرکز: `/workspace/help`؛ مقاله: `/workspace/help/{topic}`. پیوند «راهنمای همین صفحه» در نوار مشترک تمام صفحات قبلی قرار دارد. محتوا و assets در اسمبلی وب embedded هستند و CDN/اینترنت برای نمایش راهنما لازم نیست؛ این به معنی service worker یا استفاده بدون دسترسی به سرور سازمان نیست.

۳۹ مقاله: ۳۸ مسیر قبلی + خود راهنما؛ aliasهای تقویم/شیفت و کارتابل/تاریخچه موضوع مجزا دارند و محدودیت فرم مشترک توضیح داده شده است. هر مقاله شامل نقش/دسترسی، پیش‌نیاز عملیاتی در مراحل، روند استفاده، فیلدها/ستون‌ها، دکمه‌ها، نمونه، خطا و محدودیت است. ۴۶۱ شرح فیلد/کنترل/ستون ثبت شده؛ شمارش، ادعای ۴۶۱ قابلیت مستقل نیست. متن راهنما برای موارد تشخیصی و ساخته‌نشده صریح است.

JSON خام راهنما asset عمومی نیست؛ فهرست و متن از `/help/topics` و `/help/topic/{slug}` بر اساس مجوز جاری سرور فیلتر می‌شوند. کاربر ناشناس فقط مقالهٔ ورود را می‌گیرد؛ دریافت مستقیم مقالهٔ نقش‌ها بدون مجوز 403 است. موضوع ناموجود 404 است. جست‌وجو فقط روی موضوعات مجاز است. متن با DOM/textContent و بدون innerHTML رندر می‌شود. لینک راهنما اجازهٔ عملیات نمی‌دهد.

محتوای آینده باید همراه کد همان برش اضافه شود. بررسی کاتالوگ تضمین می‌کند هر مسیر منطقی موجود مقاله دارد. افزودن مسیر/مجوز/قابلیت بدون آزمون و مقاله مجاز نیست.
