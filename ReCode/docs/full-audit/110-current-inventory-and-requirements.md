## ۱. سه الزام جدید، قطعی و سراسری

### N-01 — C# / .NET 10؛ نصب و اجرای ویندوز و لینوکس
- زبان پیاده‌سازی هسته C# و چارچوب `net10.0`؛ UI وب همچنان HTML/CSS/JavaScript است. .NET چارچوب است، نه نام زبان.
- شاهد موجود: `ReCode/Directory.Build.props` با `TargetFramework=net10.0` و پروژه‌های `src/IO.Domain`، `IO.Infrastructure`، `IO.Web` و `IO.Bootstrap`.
- هدف تحویل: نصب، اجرا، ارتقا و پایش روی Windows و Linux با بسته و راهنمای جدا. آزمون build/publish روی هر دو، سپس آزمون اجرای سرویس و اتصال به DB واقعی در محیط ایزولهٔ هر دو؛ صرف build یا نصب SDK کافی نیست.
- workflow فعلی `.github/workflows/io-phase02-sql-check.yml` روی `ubuntu-24.04` است؛ آزمون Windows در این workflow نیست. بنابراین «سازگاری و نصب کامل هر دو تأیید شده» ادعا نمی‌شود.
- DB فعلی SQL Server است (`IO.Infrastructure.csproj` و `Security/IdentityStorage.cs`)؛ چندسکویی به معنی پشتیبانی PostgreSQL/MySQL یا هر توزیع/معماری لینوکس نیست. توزیع/نسخهٔ Windows و Linux و معماری هدف باید هنگام طراحی بسته مشخص و تست شوند.
- SDK قدیمی COM/native دستگاه ممکن است محدودیت Windows/معماری داشته باشد. هستهٔ وب نباید به COM یا DLL ویندوزی گره بخورد. برای هر مدل، پروتکل/آداپتر سازگار با Linux یا راهکار مشخص لازم است. اگر فقط سرویس واسط Windows ممکن باشد، این **وابستگی و مغایرت با نصب کاملاً مستقل Linux** باید پیش از انتخاب راهکار با کاربر مطرح و تأیید شود؛ نه اینکه بی‌صدا Linux-only را کامل اعلام کنیم.

### N-02 — مجوز هر قابلیت + اتصال از همان ابتدا به نقش
- هر قابلیت هنگام ساخت باید مجوز واقعی داشته باشد؛ نه موکول به پایان پروژه. مشاهده/ایجاد/ویرایش/حذف/تأیید/رد/خروجی/ارسال دستگاه/عملیات حساس به‌اندازهٔ نیاز جدا شوند.
- مجوز در کاتالوگ سرور و صفحهٔ نقش‌ها ثبت، به نقش مربوط متصل و از UI قابل اعطا/لغو باشد. دسترسی پیش‌فرض حداقلی؛ اتصال نقش به قابلیت، به معنی اعطای خودکار به همهٔ حساب‌ها نیست.
- نگاشت **نقش ← مجوز ← صفحه/منو ← عملیات API ← دامنهٔ خود/تیم/سازمان** باید قابل بررسی باشد. نام نقش به‌تنهایی مجوز محسوب نمی‌شود. سرور در هر درخواست حق عملیات و دامنه را کنترل کند.
- لغو مجوز/نقش باید در درخواست بعدی مؤثر باشد؛ منو به‌روز و دادهٔ ممنوع پاک شود. دریافت مستقیم URL/API یا خروجی فایل نباید محدودیت را دور بزند. صفحهٔ عمومی ورود/راهنمای عمومی استثنای آگاهانه است، نه مجوز داده.
- نقش‌های مقصد: کارمند، مدیر واحد، مدیریت سامانه، مدیر ارشد و اپراتور دستگاه با دسترسی محدود. نقش‌های عملیاتی مقصد با template/seed نقش در DB و انتساب کاربران فرق دارند؛ template باید قابل مدیریت و حداقلی باشد و ارتقا نباید مجوز لغوشده توسط ادمین را خودکار برگرداند.

### N-03 — راهنمای جامع داخل سامانه، صفحه‌محور و نقش‌محور
- مسیرهای پیشنهادیِ هنوز ساخته‌نشده: `/workspace/help` برای مرکز راهنما و `/workspace/help/{topic}` برای مقالهٔ هر موضوع؛ مسیر نهایی در F03 تثبیت می‌شود.
- مرکز راهنما با فهرست مرتب، جست‌وجو، مسیر راهنما در منو و لینک «راهنمای همین صفحه»؛ محتوای فارسی و قابل استفاده در نصب بدون اینترنت.
- ترتیب راهنما: شروع و ورود → نقش و دسترسی → ساختار سازمان → شیفت/تقویم → دستگاه و تردد → اصلاح/تأیید → محاسبه/مرخصی → پاداش/مکان → گزارش/فایل → پشتیبان/عملیات.
- برای **هر صفحه و زیرصفحه**: مخاطب/نقش، پیش‌نیاز، مجوز، فیلدها و معنای آن‌ها، دکمه‌ها، ترتیب استفاده، نمونه، خطاها، اثر تغییر/حذف، محدودیت و مرحلهٔ بعد توضیح داده شود. پوستهٔ موجود با قابلیت آماده‌نشده اشتباه نشود.
- راهنمای کارمند/مدیر/ادمین/مدیر ارشد/اپراتور جدا و مطالب حساس عملیات/تنظیمات محدود شود؛ اسناد و فایل دانلودی حساس نیز همان کنترل دسترسی را داشته باشند.
- این راهنما همراه هر برش تکمیل شود؛ تکمیل متن همهٔ اجزای موجود، یک کار مستقل و الزامی ابتدای ادامه است. لینک راهنما هیچ مجوز عملیاتی جدیدی نمی‌دهد.

### کمبودهای مشخص اتصال نقش/مجوز در همین کد
- `/workspace/capabilities` فقط سه پرچم employee/manager/admin می‌سازد؛ پنل جداگانهٔ executive/operator ندارد. `Ui/Index.html` پیوند executive-home را در گروه admin گذاشته؛ این معادل پنل اختصاصی مدیر ارشد نیست.
- نمایش منوهای داخل هر گروه در Index.html عمدتاً ثابت است؛ مجوز یکی از بخش‌های ادمین می‌تواند کل فهرست گروه را نشان دهد، هرچند سرویس عملیات غیرمجاز را رد می‌کند. برای خواستهٔ جدید، هر منو/دکمه هم باید از capability همان عمل تبعیت کند.
- مجوزهایی مثل `identity.manage`، `organization.manage`، `schedule.manage` و `attendance.ingest` درشت‌دانه‌اند؛ توضیح همین محدودیت در `Ui/roles.js` آمده است. وجود یک مجوز کلی به معنی تفکیک مشاهده/ویرایش/حذف نیست.
- سه مجوزی که در allowlist سرور `IdentityAdministration.GrantPermissionAsync/RevokePermissionAsync` و ثابت سرویس‌ها هستند، ولی انتخاب‌گر `roles.js` عرضه نمی‌کند: `correction.edit.self`, `leave.request.decide`, `leave.request.submit`. بنابراین «تمام مجوزهای موجود از صفحه نقش قابل اعطا/لغو هستند» فعلاً صحیح نیست.
- bootstrap در `Security/IdentityServices.cs` نقش `Initial administrator` با دو مجوز اولیه می‌سازد؛ این شاهد seed کامل همهٔ نقش‌های عملیاتی مقصد نیست.
- `/panel` در `Program.cs` دارای `AllowAnonymous()` است؛ پوستهٔ ابزار عمومی است، نه شاهد صفحهٔ محافظت‌شدهٔ اختصاصی ادمین. مجوز داده/عملیات جدا بررسی می‌شود؛ تعیین تکلیف پوسته و منوی آن در F02 لازم است.

## ۵. سه برش پایه قبل از ساخت قابلیت‌های بعدی

برنامهٔ قبلی S01..S33 حذف یا شماره‌گذاری مجدد نمی‌شود. سه پیش‌نیاز جدید از همین ابتدا وارد مسیر شدند:

| ترتیب جدید | تحویل | شرط پایان |
|---|---|---|
| F01 — پایهٔ چندسکویی | تثبیت .NET 10، ماتریس build/test/publish Windows و Linux، انتخاب محیط هدف و ثبت وابستگی‌های بومی | هر دو سیستم در CI آزموده شوند؛ وضعیت run و publish معلوم؛ محدودیت SDK صریح؛ نصب کامل دو سیستم تا S29 همچنان در انتظار پذیرش است |
| F02 — نقش/دسترسی موجود | همگام‌سازی کاتالوگ سرور/UI، ماتریس عملیات/دامنه، تفکیک مجوزهای لازم، templateهای قابل مدیریت نقش‌های مشخص، منو/پنل متناسب از همین ابتدا | کارمند/مدیر/ادمین/مدیرارشد نمونه با حداقل مجوز، اعطا و لغو از UI و درخواست مستقیم API آزموده شوند؛ اپراتور تا ساخته‌شدن دستگاه مجوز خیالی مؤثر نگیرد؛ seed ارتقا لغوهای مدیر را بازنگرداند |
| F03 — راهنمای موجودی فعلی | ساخت مرکز راهنما و راهنمای دقیق همهٔ ۳۸ مسیر موجود؛ ساختار مستقل نقش‌ها و راهنمای هر صفحه | هر مسیر موجود به مقالهٔ درست برسد؛ نقش/فیلد/دکمه/خطا/مثال توضیح داده شود؛ قابلیت ناقص صریح باشد؛ جست‌وجو/مجوز/آفلاین آزموده شود |

**ترتیب جاری: F01 → F02 → F03 → S01 → S02 … → S33**؛ در مجموع ۳۶ برش با احتساب سه پایهٔ جدید. در هر S جدید مجوز، نگاشت نقش، منو و مقالهٔ راهنما هم‌زمان ساخته می‌شود؛ نه کار عقب‌افتادهٔ انتهای پروژه. S29 و S30 نصب/اجرا و عملیات واقعی هر دو سیستم‌عامل را می‌بندند؛ F01 به‌تنهایی تضمین استقرار کامل نیست.

## ۶. تعریف جدید «تمام شد» برای هر قابلیت
**مدل/DB + منطق + API + مجوز قابل اعطا/لغو + اتصال به نقش و دامنه + منو/فرم + راهنمای همان قابلیت + تست مرتبط Windows/Linux + تست SQL/مرورگر + آدیت/خطا + CI نهایی موفق.**

آزمون لغو مجوز با نشست قبلی و فراخوانی مستقیم API/خروجی الزامی است. داشتن HTML یا گزارش سبز قبلی، جای تست قابلیت جدید را نمی‌گیرد. نتیجهٔ هر برش با کامیت، CI، مسیر مشاهده و موارد مسدود گزارش می‌شود.
