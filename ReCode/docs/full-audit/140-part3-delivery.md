# بخش۳ — S04 معرفی چند دستگاه و مجوز اپراتور

## وضعیت

**پیاده‌سازی اولیه؛ در انتظار پذیرش واقعی CI، هنوز accepted نیست.** بخش۲ با شاهد موفق مستقل بسته شده است؛ این سند نتیجهٔ بخش۲ را به کد تازه تعمیم نمی‌دهد. در این برش فقط S04 ساخته می‌شود؛ S05 اتصال و آداپتر اجرا نشده‌اند.

## قرارداد

- مسیر `/workspace/devices` موجودی واقعی DB و پروفایل تأییدنشده است. هر دستگاه UUID، شمارهٔ یکتای سراسری نرمال‌شده، محل نصب معتبر، یک منبع مستقل EventSources و rowversion دارد. شماره حتی پس از غیرفعال‌کردن آزاد نمی‌شود.
- ایجاد با UUID و fingerprint غیرمحرمانه idempotent است؛ retry متفاوت/actor متفاوت رد می‌شود. تغییر metadata و رمز با rowversion از overwrite جلوگیری می‌کند. برای قطع پاسخ ویرایش/رمز ابتدا بازخوانی لازم است.
- محل از Sites و شرکت/منطقهٔ زمانی آن انتخاب می‌شود. تغییر محل پس از raw/mapping/conflict مسدود است؛ disable و ثبت تازه لازم است تا سابقه تغییر شرکت ندهد.
- مجوزها مستقل و سراسریِ مدیریت موجودی‌اند: `devices.read/create/update/credentials.manage`. فیلتر شرکت محدودهٔ امنیتی نیست. `attendance.ingest` و نام نقش هیچ‌یک را ارث نمی‌دهند. برای اپراتور محدود به چند دستگاه، این مجوزهای سراسری مناسب نیستند؛ تخصیص محدود دستگاه در S04 ساخته نشده است.
- مجوزهای `devices.receive/send/settings/sensitive` در کاتالوگ قابل اعطا/لغو هستند ولی هیچ عملیات سخت‌افزاری در این برش موجود نیست؛ capabilities حق اعطاشده را از available=false جدا نشان می‌دهد. قالب تازهٔ اپراتور فقط read دارد؛ admin فقط چهار عملیات ساخته‌شده را می‌گیرد. قالب قبلی یا مجوز لغوشده خودکار بازگردانده نمی‌شود.
- رمز ارتباط در جدول جدا و با ASP.NET Data Protection و purpose وابسته به device id محافظت می‌شود؛ هیچ GET برای plaintext یا ciphertext وجود ندارد. آدیت فقط نوع عمل و UUID دارد، نه بدنه/رمز. فیلد رمز پس از ارسال پاک می‌شود؛ null فقط پاک‌کردن صریح است و رشتهٔ خالی رد می‌شود.
- key ring باید پایدار و دارای ACL/پشتیبان/حفاظت در حالت سکون متناسب Windows/Linux باشد. کلید و DB را کنار هم بی‌حفاظ نگه ندارید. از دست‌رفتن کلید نیاز به تنظیم مجدد رمز دارد. تغییر discriminator یا مسیر کلید هنگام استقرار باید برنامه‌ریزی شود؛ این برش تنظیم global application name موجود را تغییر نمی‌دهد.
- ثبت/ویرایش هیچ اتصال خروجی، شبکه‌پویی، تردد مصنوعی یا فرمان درب تولید نمی‌کند. پروفایل zk-standalone به host بدون URL و port معتبر نیاز دارد؛ zk-push/offline-file host/port ندارند. مدل صرفاً اعلامی و وضعیت ارتباط not-tested است.
- حذف رکورد و downgrade مخرب پس از ایجاد دستگاه در DB مسدود است؛ disable جای حذف است. migration دو جدول می‌افزاید؛ دادهٔ legacy جابه‌جا/حذف نمی‌شود.

## آزمون و راهنما

- ۲۴ check سرویس SQL افزوده: دو دستگاه/دو منبع، retry، تعارض شماره، نسخه، مجوز مستقل/لغو/غیرفعال، secret protect/purpose/lost keys، جابه‌جایی سابقه، هم‌زمانی، آدیت امن، downgrade.
- ۸ check واقعی HTTPS افزوده: ناشناس/CSRF، grant/revoke بدون relogin، ایجاد مستقل، edit، secret، capability، help/menu؛ gate از ۳۶۶ به **۳۹۸ PASS مورد انتظار** افزایش یافته است (هنوز شاهد موفقیت نیست).
- Foundation از ۲۹ به **۳۳ check**؛ کاتالوگ فعلی **۸۴ مجوز و ۴۱ صفحه/مقاله**. نقش‌ها، پنل فنی قدیمی و منوی اپراتور هم‌زمان به‌روز شدند.
- Playwright: ایجاد دو دستگاه، ویرایش، تنظیم رمز، خالی‌شدن فیلد و not-tested بودن ارتباط؛ health صفحهٔ جدید نیز بررسی می‌شود.
- DOM mock مستقل `device-ui-check.cjs`: متن امن، retry ثابت، منع payload متفاوت، کنترل پروفایل، پاک‌کردن رمز و داده پس از revoke؛ موفق محلی، جایگزین SQL/HTTPS نیست.
- راهنمای کامل `/workspace/help/devices` شامل تمام فیلدها، دکمه‌ها، خطاها، مثال، محدودیت مجوز سراسری و حفاظت key ring است.

## گام پذیرش

اجرای CI همان کد، رفع هر شکست، ثبت نتیجهٔ Windows/Linux و SQL/HTTPS/browser؛ سپس وضعیت S04 به accepted تغییر کند. تا آن زمان S05 شروع و اتصال واقعی ادعا نمی‌شود. مدل/firmware، روش ارتباط، OS سرویس و دستگاه آزمایشی هنوز برای S05 لازم‌اند؛ رمز را در چت نفرستید.

## بازبینی پس از نخستین CI

Windows/Linux `43107965251` روی `0a0ff6b` موفق شد؛ snapshot، migrationهای ۲۳گانه و ایجاد/rollback/recreate هر ۴۶ جدول در SQL `43107965407` موفق بودند، ولی مرورگر در انتظار ردیف دستگاه تازه متوقف شد. برای یافتن علت واقعی، تست سرویس دستگاه قبل از HTTP (و پس از آزمون upgrade) اجرا می‌شود و تست مرورگر اکنون اعتبار کنترل‌های فرم، پاسخ دقیق POST و خطای list را جدا گزارش می‌کند؛ شرط نمایش دستگاه حذف یا timeout بیشتر نشده است.

هم‌زمان دو مرز امنیتی تقویت شد: با رمز ذخیره‌شده، تغییر host/port/profile مسدود است تا رمز از راه metadata به مقصد دیگری نرود؛ ابتدا باید با مجوز مستقل رمز پاک شود. فیلد Secret در قرارداد JSON باید حضور صریح داشته باشد؛ حذف اتفاقی property دیگر به معنای پاک‌کردن رمز نیست. آزمون‌های موجود این دو مورد را هم الزام می‌کنند.

علت واقعی شکست ایجاد دستگاه در SQL `43108899848` مشخص شد: CHECK شماره، خط تیرهٔ مجاز برنامه را با pattern نامناسب SQL رد می‌کرد. مدل، snapshot و migration هم‌زمان اصلاح شدند: برای آزمون مجموعهٔ نویسه‌ها خط تیره ابتدا با REPLACE حذف می‌شود و بقیه به ASCII مجاز محدود می‌ماند؛ طول بایتی نیز فاصلهٔ انتهایی را رد می‌کند. آزمون SQL مستقیمِ شمارهٔ نامعتبر کنار fixtureهای معتبر دارای خط تیره افزوده شد. pattern HTML هم برای قواعد Unicode-v مرورگر، خط تیرهٔ escape‌شده دارد. این اصلاح validation را حذف یا آزاد نکرده است.
