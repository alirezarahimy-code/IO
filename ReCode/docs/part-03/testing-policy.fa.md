# سیاست آزمون کم‌تکرار بخش سوم

هدف، حذف تکرار و انتظار غیرضروری است؛ نه سبز نشان‌دادن آزمونی که اجرا نشده یا حذف کنترل‌های مجوز/تاریخچه/ثبت تکراری. این تغییر در CI است، نه قابلیت تازهٔ دستگاه و نه تکمیل بخش سوم.

## انتخاب آزمون

| نوع تغییر در push | اجرای خودکار |
|---|---|
| فقط `ReCode/docs/**` یا فایل Markdown | بررسی سبک صحت موجودی قابلیت‌ها و شواهد مرجع؛ بدون build، SQL، worker یا نصب وابستگی مرورگر |
| فقط `IO.Web/Ui/**` به‌جز `HelpContent.json` یا فایل‌های `*-ui-check.cjs` | بررسی syntax جاوااسکریپت و هر ۱۵ فایل قرارداد DOM آفلاین؛ بدون SQL/worker |
| فقط `ReCode/preview/**` | بررسی صفحهٔ مستقل با Chromium؛ بدون SQL/worker |
| `HelpContent.json` | مجموعهٔ کامل؛ کاتالوگ راهنمای مبتنی بر مجوز، قرارداد C# نیز دارد |
| سرور، مجوز، schema/migration، worker، قرارداد native، تست C#، پروژه/SDK، deploy یا فایل ناشناخته | SQL کامل و ویندوز/لینوکس حفظ می‌شود |
| ترکیب مستندات/رابط با تغییر سرور | تغییر کم‌ریسک، تغییر سرور را پنهان نمی‌کند؛ مجموعهٔ کامل اجرا می‌شود |

فیلترها در دو workflow سنگین از نوع محافظه‌کارانه‌اند: پیش‌فرض همه‌چیز مشمول است و فقط مسیرهای کم‌ریسکِ نام‌برده مستثنا می‌شوند. workflow سبک مستقل، مستندات/رابط/preview را پوشش می‌دهد. برای تشخیص تغییرات سبک، کل بازهٔ `before..after` همان push خوانده می‌شود، نه فقط آخرین commit؛ تاریخچهٔ ناموجود یا push اولیه موجب اجرای همهٔ بررسی‌های سبک می‌شود.

`concurrency` بر اساس نام workflow و همان ref است: push تازه اجرای قدیمی همان شاخه را لغو می‌کند، نه workflow دیگر را. اجرای لغوشده شاهد موفقیت نیست و ممکن است بخشی از هزینهٔ شروع‌شده را مصرف کرده باشد. تغییر خود workflowها این بار عمداً همهٔ بررسی‌ها را فعال می‌کند.

## حذف اجرای تکراری آزمایشگاه

مجموعهٔ کامل SQL از قبل `VirtualWorkerTests` و `LegacyPollScheduleTests` را اجرا می‌کند. اجرای پیش‌فرض اکنون آن‌ها را بار دوم روی دیتابیس مستقل preflight تکرار نمی‌کند. تست کامل، خطای واقعی را همچنان با exit ناموفق و شمارش سخت‌گیرانهٔ `phase03-report-tests.py` گزارش می‌دهد. شمارش مصوب فعلی ۸۵۱ خط نام‌دار است و این بهینه‌سازی عدد را کاهش نداده است.

برای تشخیص وابستگی به fixtureها یا مشکل isolation، اجرای جداگانهٔ دیتابیس خالی حذف نشده؛ انتخابی است:

- `full`: پیش‌فرض؛ کل SQL شامل مسیر مرورگر/worker، بدون preflight تکراری.
- `virtual-worker`: بررسی‌های مشترک workflow و آزمایشگاه SQL/HTTPS/Chromium/worker روی دیتابیس خالی؛ بدون اجرای کل regression SQL. summary صریحاً می‌گوید SQL کامل اجرا نشده است.
- `full-with-preflight`: ابتدا آزمایشگاه مستقل و سپس کل SQL؛ فقط برای بررسی isolation یا پذیرش تجمیعی لازم.

workflowهای سنگین و سبک `workflow_dispatch` دارند. وقتی GitHub امکان dispatch این workflow را در مخزن فراهم کند، نمونهٔ درخواست برای **همین شاخهٔ کاری**:

```bash
gh workflow run io-phase02-sql-check.yml --ref arena/5496cceb-io -f suite=virtual-worker
gh workflow run io-phase02-sql-check.yml --ref arena/5496cceb-io -f suite=full-with-preflight
gh workflow run io-cross-platform.yml --ref arena/5496cceb-io
```

GitHub معمولاً وجود `workflow_dispatch` روی شاخهٔ پیش‌فرض را برای dispatch لازم دارد؛ تا ثبت/ادغام آن، نباید صرف وجود این ورودی در شاخهٔ کاری را شاهد امکان اجرای دستی از API دانست. pushهای مشمول فیلتر همچنان خودکار اجرا می‌شوند. خطای dispatch یا اجرای skipped/cancelled به معنی آزمون موفق نیست.

## هنگام توسعه و تحویل

- اصلاحات کوچک یک برش، ابتدا محلی و به‌صورت تجمیعی آماده می‌شوند؛ هر ویرایش کوچک push مستقل لازم ندارد.
- برای صفحهٔ مشخص می‌توان تنها فایل DOM مربوط را اجرا کرد؛ پیش از تحویل رابط، runner مشترک همهٔ ۱۵ قرارداد آفلاین را ظرف چند ثانیه بررسی می‌کند:

```bash
# jsdom@26.1.0 باید در NODE_PATH یا مسیر معمول Node نصب باشد.
node ReCode/tests/IO.Infrastructure.SqlTests/device-schedules-ui-check.cjs
bash ReCode/tools/check-ui-dom.sh
# آزمون سیاست CI، بدون اجرای واقعی dotnet/SQL:
# PyYAML==6.0.3 لازم است.
python3 ReCode/tools/ci-policy-tests.py
```

- در تغییر مسیرهای مشترک/امنیتی، تست کامل کم نمی‌شود؛ در اصلاح متوالی، اجرای قدیمی دیگر نباید بیهوده ادامه یابد.
- قبل از پذیرش تجمیعی بخش، مجموعهٔ کامل و ویندوز/لینوکس روی همان SHA لازم است؛ تست DOM جای مرورگر واقعی/سرور نیست. اگر رابطی در مسیر حساس تأیید/مجوز تغییر کند، بررسی یکپارچگی مرتبط نیز لازم است؛ صرف UI بودن مسیر دلیل کفایت DOM برای پذیرش نهایی نیست.
- تحویل کوتاه باید SHA، تست‌های واقعاً اجراشده و موارد اجرا‌نشده/درحال‌اجرا را جدا کند. صرفه‌جویی زمانی تخمینی، benchmark یا تضمین سرعت نیست.

## آزمون خود سیاست

`ci-policy-tests.py` چهارده بررسی دارد: مسیر مستندات/رابط/preview، استثنای کاتالوگ مجوز، تغییر مخلوط، مسیر ناشناخته، dispatch/concurrency، diff چندcommitی و تاریخچهٔ ناموجود. شاخه‌های واقعی shell اجرای SQL نیز با `dotnet` مصنوعی اجرا می‌شوند تا ثابت شود حالت full فقط یک‌بار اجرا می‌کند، حالت focused ادعای full ندارد و خطا/نام حالت نامعتبر به موفقیت تبدیل نمی‌شود. این تست مصنوعی، شاهد SQL یا دستگاه نیست.

شواهد قبلی دستگاه در `s10-legacy-polling-evidence.json` تاریخی و متعلق به SHA خود باقی می‌ماند؛ برای این تغییر CI از آن ادعای اجرای مجدد سخت‌افزار یا نرم‌افزار دستگاه نمی‌شود.

### محدودیت مشاهده‌شدهٔ dispatch در اتصال فعلی

تلاش واقعی `gh workflow run ... -f suite=virtual-worker` پاسخ `HTTP 403: Resource not accessible by integration` داد و هیچ run دستی ساخته نشد؛ این خطای دسترسی API است، نه شکست/موفقیت تست. علت آن را صرفاً نبود workflow در main فرض نمی‌کنیم. pushهای خودکار کار می‌کنند و برای اصلاح fixture جاری از همان مسیر استفاده شده است. تا رفع دسترسی dispatch، حالت focused را اجراشده معرفی نکنید یا برای همان خطا درخواست تکراری نفرستید. هیچ credential یا token در فایل/گفتگو ذخیره نشده است.
