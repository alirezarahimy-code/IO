# تصمیم اجرا: پایان نرم‌افزار با آزمایشگاه مجازی؛ Windows واقعی در انتها

## تصمیم کاربر

کاربر دوباره تصریح کرد که اجرای واقعی Windows/SDK و دستگاه فیزیکی فعلاً به پایان کار موکول است. کدهای دو برنامهٔ مرجع در سازمان فعال و آزموده‌اند و استفاده/اقتباس از آن‌ها برای ادامهٔ پیاده‌سازی مجاز است. بنابراین نبود دستگاه محلی یا اجرای COM در Linux **مانع ادامهٔ توسعه یا شرط شروع برش بعدی نیست**.

- مرجع اصلی T5Web باینری است؛ decompile همان باینری و کد تاریخی AriaAdmin برای بازسازی رفتار خوانده می‌شوند. فعال‌بودن مرجع در سازمان شاهد عملی ارزشمند است؛ تطبیق قرارداد و انواع داده در .NET10 همچنان آزمون می‌خواهد.
- API یا رفتار مرجع به‌دلیل نیاز به Windows به‌تنهایی از دامنه حذف نمی‌شود. قرارداد/آداپتر نرم‌افزاری آن باید ساخته و روی محیط مجازی آزموده شود؛ آزمون SDK واقعی بعداً انجام می‌شود.
- کد قدیمی رمز یا قالب بیومتریک را در گزارش/لاگ چاپ می‌کرد یا فرمان را با HTTP200 موفق می‌نامید؛ این رفتارهای جانبی برای هم‌ارزی الزامی نیستند. حفظ مجوز، تأیید و سابقه در پیاده‌سازی جدید ضروری است.
- تأیید مجدد برای اجرای مجازی یا ادامهٔ کار خواسته نمی‌شود. کنترل فیزیکی درب و payroll همچنان خارج دامنه‌اند؛ سیاست دادهٔ بیومتریک خام از توافق تست مجازی استنتاج نمی‌شود.

## دو دروازهٔ مستقل، نه یک مانع تکراری

1. **تکمیل نرم‌افزار بخش۳**: پیاده‌سازی مانده‌های S04–S12 در دامنهٔ مصوب، رابط دیتابیس واقعی، grant/revoke، اصل داده/قرنطینه/تکرارپذیری، و تست مجازی یکپارچه. `softwareComplete` فقط پس از بستن واقعی این مانده‌ها true می‌شود.
2. **پذیرش نصب و سخت‌افزار**: Windows، SDK مجاز و دو دستگاه مدل/firmware واقعی با قطعی و بازیابی؛ طبق تصمیم کاربر در انتها اجرا می‌شود. نبود این شاهد به معنی توقف توسعه نیست. `hardwareVerified` تا اجرای آن false می‌ماند.

نباید با عقب‌انداختن دروازهٔ دوم، ماندهٔ پیاده‌سازی دروازهٔ اول را «کامل» نامید؛ همچنین نباید دروازهٔ دوم را هر بار پیش‌نیاز کار نرم‌افزاری معرفی کرد.

## آزمایشگاه یکپارچهٔ جدید

تست `VirtualWorkerTests.cs` محیط زیر را می‌سازد:

```text
Chromium واقعی + فرم صفحه
        ↓ HTTPS + cookie + CSRF
وب واقعی IO → سرویس مجوز/صف SQL واقعی
        ↓
DiagnosticWorker اصلی با چهار slot
        ↓ credential مقید + supervisor اصلی + child واقعی
دو دستگاه stateful مستقل با TCP loopback
        ↓
اصل tuple/رسید/unknown/review در SQL
```

نه fetch مرورگر mock می‌شود، نه Claim/Append/Complete به‌جای worker دستی فراخوانی می‌شوند و نه receipt یا نتیجهٔ دستگاه در SQL جعل می‌شود. برای دستگاه مصنوعی فقط یک subclass داخلی در assembly تست، شرط سیستم‌عامل worker را جایگزین می‌کند؛ انتخاب emulator از config محصول اضافه نشده است. مسیر نصب همچنان bridge اصلی و محدودیت سیستم‌عامل خود را دارد.

پروتکل آزمایشگاه JSON خصوصی است، نه emulator سازگار با پروتکل ZK و نه اجرای COM. تست جدید اتصال end-to-end **نرم‌افزار خودمان** را اثبات می‌کند؛ تطبیق vendor همچنان بر کد/باینری مرجع و آزمون واقعی مؤخر تکیه دارد. تغییر IP به شبکهٔ واقعی از آزمایشگاه loopback مجاز نشده است؛ قرارداد دو مقصد آن در آزمون‌های اختصاصی موجود پوشش دارد.

سناریوهای جدید: credential محافظت‌شده، دو snapshot کاربر، batch چنددستگاهی، نوشتن اعمال‌شده با پاسخ گم‌شده، جلوگیری از retry کور، snapshot تازه و review، ساعت مستقل، restart با executor اصلی، idle مدل‌محور با قطع ACK و recovery، قطع stream بعد از۵۰ ردیف، دو دریافت۱۰۳ردیفی از فرم مرورگر با۲۰۶ رسید و۱۰۳ raw، restart worker و لغو مجوز پیش از dispatch، و قطع دسترسی history پس از revoke.
