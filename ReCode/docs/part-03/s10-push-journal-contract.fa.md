# R08 — زیرساخت مستقل نگهداری شواهد PUSH، نه receiver امن

## تصمیم این برش

پس از واگذاری انتخاب مسیر به پیشنهاد عامل، مسیر محافظه‌کارانه انتخاب شد: زیرساخت مستقل SQL و رسید نگهداری جلو برود؛ دریافت عمومی بسته بماند. نه SDK سازنده موجود فرض شده، نه gateway احرازشده جای احراز هویت بومی دستگاه تصویب شده است. این تصمیم مجوز حذف اطلاعات یا سیاست زیست‌سنجی نیست.

## پیاده‌سازی

- migration شمارهٔ۴۸: `20261114110000_DevicePushJournal`، مدل و snapshot متناظر، با FKهای دستگاه/منبع/محل/شرکت/کاربر.
- `DevicePushJournal.RetainForReviewAsync`: فقط سرویس داخلی با کاربر فعال، حق مستقل `devices.push.retain` و دامنهٔ مجاز دستگاه؛ نه handler دستگاه و نه endpoint وب. فقط پروفایل فعال `zk-push` و نسخهٔ صریح برای عملیات جدید پذیرفته می‌شود.
- Serial ورودی **ادعاشده و تأییدنشده** است؛ شمارهٔ موجودی دستگاه به جای SN استفاده نمی‌شود. Stamp همچنان cursor کدر است، نه nonce یا شناسهٔ رویداد.
- اصل بایت‌های پیام، SHA256، قرارداد codec، snapshot تفسیر سطرها، UTC حاصل از منطقهٔ زمانی نصب، نسخهٔ دستگاه و مشخصات منبع/محل/شرکت به صورت immutable ثبت می‌شوند. بایت‌ها پیش از اولین await کپی می‌شوند. سطرهای خرابِ قابل‌رمزگشایی همراه شواهد می‌مانند؛ UTF8 نامعتبر و بودجهٔ بیش‌ازحد رد می‌شوند.
- SQL مستقل از hash داده‌شده، `HASHBYTES('SHA2_256', OriginalBody)` را بررسی می‌کند. trigger شمار سطرهای snapshot و شمار parsed را کنترل می‌کند و تغییر/حذف سابقه را می‌بندد. این کنترل معادل احراز اصالت دستگاه یا اثبات مستقل تطابق معنایی تک‌تک فیلدهای JSON با بایت‌ها نیست؛ ایجاد snapshot وظیفهٔ سرویس codec است.
- عملیات و audit در تراکنش serializable مشترک ثبت می‌شوند. `RetentionReceipt` فقط **پس از بازگشت موفق commit** ساخته می‌شود؛ state آن `retained-unverified-requires-review` است، نه processed/imported.
- حق مستقل `devices.push.read` اصل پیام و snapshot شخصی را فقط در دامنهٔ مجاز دستگاه می‌خواند. هیچ نقش پیش‌فرضی این دو حق را خودکار نمی‌گیرد؛ ثبت permission با اعطای حق متفاوت است.
- جدول دارای شواهد، downgrade مخرب را رد می‌کند. این محافظ فنی، جایگزین سیاست مصوب retention/حذف/حفاظت در محیط عملیاتی نیست. مجوز استفاده از اطلاعات واقعی استنتاج نمی‌شود.

## retry و تکرار واقعی

`OperationId` شناسهٔ **عملیات صریح اپراتور** است، نه شناسهٔ ساخته‌شده از Stamp، hash، زمان یا SN. تکرار دقیق همان عملیات با همان actor/device/version/serial/stamp/body رسید قبلی را بازمی‌گرداند. تغییر این ورودی‌ها conflict است. حق و دامنه و فعال‌بودن دستگاه در retry هم دوباره کنترل می‌شوند. تغییر بعدی قواعد منطقهٔ زمانی باعث تفسیر مجدد snapshot قدیمی نمی‌شود.

عملیات جدید با بایت‌های یکسان جداگانه حفظ می‌شود: hash شاخص جست‌وجو است، نه کلید unique. تکرار سطرهای یکسان هم با multiplicity حفظ می‌شود. **این رفتار هنوز سیاست retry شبکهٔ vendor نیست**؛ قرارداد session/شناسهٔ انتقال معتبر برای receiver بعدی لازم است. ادغام خودکار این شواهد با تردد خام یا محاسبات حقوق وجود ندارد.

## ACK ممنوع در این برش

رسید نگهداری به معنی پردازش سطرها نیست. این سرویس نه `FormatCommittedAcknowledgement` را صدا می‌زند و نه `OK: n` تولید می‌کند. وجود GUID/hash/parsedCount مجوز ACK نیست. احراز هویت، سیاست نگاشت، quarantine، رسید پردازش سطرها و ACK اتمیک باید در برش‌های بعدی تکمیل و آزموده شوند. ارتباط دستگاه/SDK، ارسال command، endpoint `/iclock` و UI دریافت ساخته نشده‌اند.

## آزمون و پذیرش

۲۴ بررسی SQL به suite کامل اضافه شده‌اند: تفکیک حقوق، رد ورودی، نسخه و پروفایل، snapshot و multiplicity، retry دقیق/تغییریافته/همزمان، عدم dedup بایت‌های یکسان در عملیات جدید، audit بدون محتوای شخصی، شکست audit پس از SaveChanges و rollback، retry پس از rollback، تثبیت منطقهٔ زمانی، scope/grant/revoke، لغو حق، دستگاه غیرفعال، hash SQL، شمار snapshot، immutability و downgrade.

انتظار reporter کامل از۹۹۱ به۱۰۱۵ به دلیل همین۲۴ بررسی تغییر کرده است؛ این عدد تا موفقیت CI دقیق همان commit شاهد اجرای موفق نیست. محلی NuGet با `NU1301` و EOF دسترسی build زیرساخت را مسدود کرده؛ نتیجهٔ CI باید مستقل بررسی شود. ۱۸ بررسی policy و auditهای reference/capability محلی موفق‌اند.

**R08 باز است؛ جمع همچنان۹ فنی R08–R16 + H01 جداست.** مرجع codec قبلی: [قرارداد ATTLOG](s10-push-attlog-contract.fa.md). هیچ پذیرش سخت‌افزاری یا تکمیل PUSH امن ادعا نمی‌شود.
