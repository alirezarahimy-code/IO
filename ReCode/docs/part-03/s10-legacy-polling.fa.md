# S10 — قالب صریح SSR/non-TFT در زمان‌بندی پایدار

این برش دریافت non-TFT مرجع را به همان مسیر زمان‌بندی SQL و worker موجود وصل می‌کند؛ polling همچنان **PUSH نیست**. آداپتر بومی همان `Personnel.ZK.ZKDevice.WriteRecordsToList` و `GetGeneralLogData` منتقل‌شده در [برش قبلی](s09-legacy-attendance.fa.md) است؛ پروتکل تازه‌ای جای SDK قرار نگرفته است. کدهای مرجع تغییر نکرده‌اند و پذیرش دستگاه واقعی در انتها باقی است.

## قرارداد ثابت از تأیید تا اجرا

`DevicePollSchedules.Input.ReadFormat` یکی از دو مقدار دقیق است:

- `ssr-v1`: پیش‌فرض سازگار با درخواست‌ها و زمان‌بندی‌های قبلی؛ شناسهٔ رشته‌ای، ثانیه و WorkCode واقعی SSR.
- `legacy-int32-minute-v1`: انتخاب صریح non-TFT مرجع؛ هویت Int32 و زمان تا دقیقه، دو خروجی machine محفوظ؛ ثانیه/WorkCode خروجی این امضا نیستند.

انتخاب از متن مدل دستگاه حدس زده نمی‌شود. قالب در تأیید اولیه، SQL، هر run و دانلود آن، claim، worker و نمایش تاریخچه ثابت می‌ماند. endpoint نصب‌شده باید همان `AttendanceReadFormat` را داشته باشد؛ mismatch به unsupported می‌رسد و طبق قرارداد موجود زمان‌بندی متوقف می‌شود، نه اینکه SSR/legacy جابه‌جا یا بی‌پایان retry شوند.

تکرار همان UUID فقط با همان قالب/مقصد/بازه/بودجه/نوع ثبت مجاز است. pause/resume فقط همان تأیید قبلی را ادامه می‌دهد؛ قالب را تغییر نمی‌دهد. برای انتخاب قالب دیگر، زمان‌بندی جدید و تأیید تازه لازم است؛ تاریخچهٔ قبلی حذف نمی‌شود.

## مسیر اپراتور

در `/workspace/device-schedules`:

1. شناسه و نسخهٔ دستگاه، **قالب منطبق با نصب worker**، شروع UTC، کدهای ورود/خروج، پنجره و overlap را مشخص کنید.
2. ثبت خودکار پیش‌فرض خاموش است. اگر آن را صریح فعال کنید، حق commit و دریافت attendance مستقل لازم‌اند؛ حق execute سرویس چنین حقی ایجاد نمی‌کند.
3. مقصد، قالب، cursor و نوع ثبت را تأیید کنید. در پاسخ نامعلوم، همان UUID و همان همهٔ داده‌ها، از جمله قالب، نگه داشته می‌شوند؛ تغییر قالب به‌عنوان retry پذیرفته نمی‌شود.
4. تاریخچهٔ زمان‌بندی و run، قالب واقعی دانلود را نشان می‌دهند؛ لینک اصل tupleها به همان snapshot و رسیدهای SQL می‌رود.
5. توقف با نسخهٔ تازه، pending را لغو و خودکارسازی را متوقف می‌کند. خواندن running قابل پس‌گرفتن تضمینی نیست. resume فقط با اختیار جاری سازنده و همان مقصد/نسخه/قالب است.

حقوق `devices.schedules.read/manage/execute` و حقوق مستقل `devices.attendance.extract/commit` و `attendance.events.receive` بدون حق تازه یا اعطای خودکار باقی‌اند. scope دستگاه منتخب در query و اجرای فعلی انسان درخواست‌کننده اعمال می‌شود. نقش انسانی سرویس نمی‌شود و تغییر نام نقش مجوز نیست.

## قطعی، هم‌پوشانی و ثبت

- هر پنجره یک intent خواندنی واقعی با `ReadFormat` همان زمان‌بندی و یک run دارای FK واقعی است. صف‌شدن به معنی جلو‌رفتن cursor نیست.
- قطع stream، timeout و شمارندهٔ ناپایدار، همان رفتار incomplete/backoff قبلی را دارند: اصل tupleهای پذیرفته‌شده می‌ماند، cursor جلو نمی‌رود، تلاش بعدی همان پنجرهٔ تأییدنشده و **همان قالب** را بازمی‌خواند؛ نوشتن دستگاه retry نمی‌شود.
- overlap از `max(StartUtc,cursor-overlap)` شروع می‌شود؛ cursor عقب نمی‌رود. receiptهای تکراری همان canonical tuple و multiplicity را استفاده می‌کنند؛ دادهٔ دیررس داخل پنجره فقط یک بار به raw می‌رود. رخداد دیررس قدیمی‌تر از overlap همچنان تضمین نشده است.
- read-only فقط دریافت کامل را تأیید می‌کند؛ خودکارسازی تنها با تأیید و حقوق مستقل، صفحه‌های واقعی raw را بررسی می‌کند. هویت منفی/ناشناس، تاریخ بد، کد نامعلوم و تاریخچهٔ قالب مختلط قرنطینه می‌مانند.
- موفقیت run به معنی ثبت همهٔ ردیف‌ها یا محاسبهٔ کارکرد نیست. اگر source قبلاً raw از قالب دیگری داشته باشد، محافظ `format-history-review-required` برش S09 همچنان جلوی ثبت خاموش قالب مختلط را می‌گیرد.
- لغو اختیار جاری سازنده، run و pending مرتبط را متوقف می‌کند؛ هیچ cursor یا رخداد فرضی برای پرکردن فاصلهٔ قطعی تولید نمی‌شود.

## ارتقای SQL و نصب

migration مستقل `20261113120000_DevicePollReadFormats`، تعداد migrationهای بنیاد را به۴۳ می‌رساند؛ جدول‌ها همچنان۶۰ و Identity migrationها۲ هستند.

1. `DevicePollSchedules.ReadFormat` غیرnullable با default سازگار `ssr-v1` اضافه می‌شود.
2. constraint، مقدار دقیق و طول باینری را کنترل می‌کند؛ فاصلهٔ انتهایی یا نام قالب ناشناخته پذیرفته نمی‌شود.
3. trigger مستقل، تغییر قالب مصوب را منع می‌کند؛ trigger دیگری اتصال run به دانلود با قالب دیگر را، حتی اگر سایر شناسه‌ها و بازه منطبق باشند، رد می‌کند.
4. اگر در تاریخچهٔ پیش از ارتقا run ناسازگار دستی وجود داشته باشد، migration آن را SSR فرض یا بازنویسی نمی‌کند و نیاز به بررسی صریح اعلام می‌کند.
5. وجود هر زمان‌بندی legacy، حتی متوقف، downgrade حذف‌کنندهٔ سابقهٔ قالب را رد می‌کند.

migrate و انتشار هماهنگ web/worker لازم‌اند؛ نصب NativeEndpoint همچنان باید صریح، serial/IP/port/machine pin و key-ring معتبر داشته باشد. default نصب برای فعال‌سازی خودکار تغییر نکرده است. bridge همان نسخهٔ tagدار برش قبلی است؛ اجرای COM روی Linux فعال نمی‌شود.

## شاهد آزمون

- `LegacyPollScheduleTests.cs`: ۱۴ بررسی نام‌دار SQL شامل مجوز، قالب ناشناخته، replay، تغییرناپذیری، جعل اتصال SSR به legacy با خطای SQL مشخص، tick واقعی، read-only، pause/resume، auto-review، partial/backoff/overlap/dedup، تاریخچه، revoke و downgrade.
- `device-schedules-ui-check.cjs`: ارسال انتخاب legacy، رد تغییر قالب در پاسخ نامعلوم، CSRF، تأیید صریح، نمایش قالب run، نسخهٔ pause و پاک‌سازی پس از لغو دسترسی.
- `virtual-worker-browser.cjs` و `VirtualWorkerTests.cs`: فرم Chromium روی HTTPS واقعی یک زمان‌بندی legacy با ثبت خودکار می‌سازد؛ worker و child و endpoint مجازی stateful واقعاً اجرا می‌شوند. دانلود۱۰۳ tuple، review سه‌صفحه‌ای، cursor تا۹:۰۰، pause نسخه‌دار و۱۰۳ receipt جدید SQL سنجیده می‌شود؛ raw قبلی دوباره تولید نمی‌شود.
- این سناریو علاوه بر دیتابیس خالی preflight، در مجموعهٔ کامل SQL نیز اجرا می‌شود. نتیجه و SHA دقیق در [شاهد CI این برش](s10-legacy-polling-evidence.json) ثبت می‌شوند؛ تست مجازی اثبات اجرای COM یا مدل/firmware سازمان نیست.

جزئیات مرجع و هش باینری/decompile در [شاهد انتقال non-TFT](s09-legacy-attendance-evidence.json) باقی است. این برش نرم‌افزاری نه PUSH امن را تکمیل می‌کند، نه تنظیمات/RemoteEnroll/عملیات حساس باقی‌مانده را، و نه بخش سوم را کامل اعلام می‌کند.
