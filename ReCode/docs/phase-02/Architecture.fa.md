# معماری اولیهٔ قابل پیگیری — فاز ۲

## اصول

طبق مانیفست، محصول یک **مونولیت ماژولار** با قرارداد مشخص بین حوزه‌هاست، نه مجموعه‌ای از سرویس‌های مستقل. هدف اجرا در Linux روی .NET 10، ASP.NET Core، EF Core و SQL Server است. رابط هر دو پنل وب است. دو پنل مرز دسترسی‌اند نه ضرورتاً دو برنامهٔ مستقر مستقل. build اسکلت و اتصال SQL آزمایشی جداگانه موفق شده‌اند؛ این سند اثبات اتصال برنامه به SQL یا سازگاری دستگاه نیست.

## آنچه اکنون واقعاً در مخزن است

| جزء | مسئولیت موجود | وابستگی فعلی | محدودیت |
|---|---|---|---|
| `IO.Domain` | اشیای مقدماتی انتساب سازمانی و دادهٔ خام تردد و یک قرارداد ذخیره. | کتابخانهٔ استاندارد .NET. | ذخیره‌سازی، اعمال مجوز، تراکنش، محاسبه و تکرارزدایی پیاده نشده‌اند؛ سیاست‌های دامنه نیازمند تأییدند. |
| `IO.Web` | میزبان اولیه و دو پاسخ وضعیت. | ارجاع پروژه به `IO.Domain`. | احراز هویت، مجوز و دو پنل ندارد؛ برای تولید یا دادهٔ واقعی مناسب نیست. |
| `IO.Domain.Tests` | ۱۵ بررسی کنسولی مستقل. | `IO.Domain`. | هر ۱۵ بررسی در Linux موفق بودند؛ چارچوب تست متداول، SQL، تست API و امنیتی نیست. |

`Directory.Build.props` هدف `net10.0`، nullable و تبدیل هشدار به خطا را اعمال می‌کند. `global.json` فقط انتخاب SDK را هدایت می‌کند.

## مرزهای هدف، نه اجزای ساخته‌شده

- **هویت و دسترسی:** هویت، مجوز سمت سرور و محدودهٔ سازمانی؛ رعایت حداقل دسترسی، بدون حساب/رمز پیش‌فرض.
- **سازمان و تقویم:** پرسنل، انتساب تاریخ‌دار، شیفت و منطقهٔ زمانی سایت.
- **حضور و محاسبه:** دریافت رویداد خام، اصلاح مستقل با تصمیم مجاز، نسخهٔ قواعد، اجرا و نتیجهٔ قابل ردیابی؛ عدم حدس فرمول.
- **گردش‌کار و گزارش:** درخواست و تصمیم، تأیید کارکرد و خروجی حقوق از دادهٔ تأییدشده.
- **ادغام دستگاه:** دریافت از آداپتور مستقل، ZKTeco در دامنه؛ Virdi/UNIS مشروط به بررسی. رخداد دسترسی فیزیکی از رخداد حضور مجزاست؛ فرمان فیزیکی نیازمند تأیید و طراحی ایمنی.
- **زیرساخت:** پیاده‌سازی ذخیره‌سازی و مجوز و قابلیت رصد در مرزهای صریح؛ اسرار از تنظیمات امن، نه مخزن یا log. همهٔ جزئیات پیاده‌سازی در فاز مربوط تعیین و تست می‌شوند.

این فهرست طراحی منطقی و هدف است، نه الزام به ساخت پروژهٔ جدا برای هر مورد. رابط وب تنها نقطهٔ اعمال امنیت نیست؛ همهٔ ورودی‌ها شامل API و عملیات پس‌زمینه نیز باید همان سیاست مجوز را اجرا کنند. دادهٔ خام، اصلاح، نتیجهٔ محاسبه و خروجی تأییدشده موجودیت‌های جدا هستند.

## مسیر وابستگی پیشنهادی

میزبان وب → قراردادها و منطق کاربرد → دامنه؛ زیرساخت قراردادهای موردنیاز را پیاده می‌کند و در میزبان ترکیب می‌شود. **لایهٔ کاربرد و زیرساخت هنوز ساخته نشده‌اند.** دامنه نباید به UI، جزئیات SQL یا SDKهای دستگاه وابسته شود. قراردادها هنگام اجرای هر فاز با تست و بدون ادعای سازگاری نمونهٔ قدیم تعیین می‌شوند.

## تصمیم‌های باز و آزمون

نسخهٔ SQL Server آزمایشی، سیاست‌های مجوز و تاریخچه، قواعد محاسبه و رابط واقعی دستگاه‌ها در [دفتر تصمیم فاز ۱](../phase-01/Decisions-and-Risks.fa.md) بازند. تست پایه باید ساخت در Linux و بررسی دامنه را واقعاً اجرا کند؛ تست SQL واقعیِ آزمایشی برای قیود و هم‌زمانی در فاز مربوط جداگانه لازم است. طرح حاضر تأیید تجاری، امنیت پویا، کارایی یا آمادگی تولید محسوب نمی‌شود.
