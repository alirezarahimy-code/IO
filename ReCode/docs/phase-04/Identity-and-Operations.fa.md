# فاز ۴ — هویت، مجوز و راهنمای عملیات ایمن

**فقط بنیاد آزمایشی؛ استقرار یا استفاده با دادهٔ واقعی مجاز و آماده نیست.** این سند رفتار فعلی را از تصمیم نهایی کسب‌وکار و کنترل‌های تولید تفکیک می‌کند. مسیرهای کد: `src/IO.Infrastructure/Security/`، `src/IO.Infrastructure/IdentityMigrations/`، `src/IO.Web/` و `src/IO.Bootstrap/`.

## رفتار اجراشده

| موضوع | رفتار کنونی |
|---|---|
| فعال‌سازی | هویت وب پیش‌فرض **خاموش** است. با `IO__EnableExperimentalIdentity=true` و تنظیم صریح `ConnectionStrings__IO` فعال می‌شود. برنامه هیچ migration یا ایجاد حساب خودکار انجام نمی‌دهد؛ `/panel` و endpointهای هویت بدون فعال‌سازی وجود ندارند. |
| ورود | ASP.NET Core Identity رمز هش‌شده و سیاست پیش‌فرض پیچیدگی با طول حداقل ۱۴ و چهار نویسهٔ متفاوت دارد؛ کاربر و رمز به‌ترتیب حداکثر ۲۰۰ و ۲۵۶ نویسه‌اند. هویت به رکورد کاربر فعال با همان GUID وصل باید باشد. پنج تلاش ناموفق سبب قفل ۱۵ دقیقه‌ای Identity می‌شود. خطاهای ورود پاسخ عمومی دارند، اما مقاومت در برابر تشخیص نام کاربری از زمان پاسخ ارزیابی نشده است. |
| رمز اولیه | مدیر حساب را با رمز اولیه می‌سازد؛ حساب پس از ورود تا تغییر آن فقط می‌تواند به صفحه، CSRF، وضعیت خود، تغییر رمز و خروج دسترسی داشته باشد. رمز جدید نمی‌تواند عین رمز فعلی باشد. تغییر رمز حسابرسی و همهٔ نشست‌ها با تغییر security stamp بی‌اعتبار می‌شوند. ایجاد اولین مدیر استثناست: خود مدیر از ابتدا رمز خود را انتخاب می‌کند. |
| نشست و CSRF | کوکی `__Host-IO.Session` با Secure، HttpOnly، SameSite Strict و انقضای ۳۰ دقیقه بدون تمدید لغزشی؛ stamp و وضعیت فعال در هر درخواست بررسی می‌شوند. خروج stamp را تغییر می‌دهد و **همهٔ نشست‌های آن حساب** را می‌بندد. تغییر وضعیت فعال/غیرفعال نیز stamp را می‌چرخاند تا کوکی قدیمی پس از فعال‌سازی دوباره زنده نشود. POSTها دارای token ضد CSRF هستند. درخواست‌های identity با HTTP رد می‌شوند. |
| محدودسازی | ورود به ازای IP مشاهده‌شده توسط سرور ۳۰ درخواست در دقیقه؛ تغییر رمز به ازای حساب پنج درخواست در دقیقه. پاسخ محدودیت ۴۲۹ است. این محدودسازها در حافظهٔ همان فرایندند، نه سراسری و پایدار؛ قفل حساب Identity در SQL ذخیره می‌شود. |
| مجوز | دسترسی به پرونده برای حساب فعال، فقط با مجوز صریح خود، واحد دقیق معتبر یا سراسری؛ بدون مجوز/هدف، پاسخ یکسان ۴۰۴ است. مدیریت هویت فقط با مجوز دقیق `identity.manage`، بدون اتکا به نام نقش. تطبیق کدها با collation باینری و طول بایت انجام می‌شود. تاریخ جاری برای scope فعلاً UTC است و child-unit ضمنی مجاز نیست. |
| مدیریت | ایجاد حساب و نقش، فعال/غیرفعال، اعطا/لغو نقش و مجوز و scope، و فهرست‌های محدود به ۱۰۰ رکورد برای دارندهٔ `identity.manage`. مدیر نمی‌تواند نقش خودش، مجوز نقشی که خودش عضو آن است یا حساب خودش را از این مسیر حذف/غیرفعال کند. اعطای `identity.manage` به دیگری دسترسی مدیریتی سراسری می‌دهد و باید عملیاتی حساس تلقی شود. تغییر نام کاربر/نقش، حذف نقش، reset رمز توسط مدیر، MFA و گردش بازیابی فعلاً وجود ندارند. |
| حسابرسی | راه‌اندازی، تغییرات مدیریتی و رمز و مشاهدهٔ فهرست audit با عامل، عمل/هدف و زمان UTC در تراکنش ثبت می‌شوند؛ رمز ثبت نمی‌شود. همهٔ شکست‌ها، ورودها و دادهٔ قبل/بعد کامل ثبت نمی‌شوند. جدول قابل تغییر توسط حساب دارای مجوز SQL است؛ عدم امکان دستکاری یا انکارناپذیری تضمین نشده است. |

فرم‌ها و API فعلی محدود به فاز هویت هستند؛ UI آنها ساده و مبتنی بر شناسه است. شماره/پروندهٔ کارکنان و سازمان باید در فازهای مربوط تکمیل شود. سطح دسترسی همهٔ قابلیت‌های آینده باید صریح طراحی و اجرا شود؛ مجوز `employees.read.all` به‌خودی‌خود مجوز همهٔ عملیات آینده نیست.

## migration و راه‌اندازی ایمن

دو context در یک دیتابیس هستند ولی جدول history جدا دارند: `IoDbContext` از `__EFMigrationsHistory` و `LoginIdentityDbContext` از `__IdentityMigrationsHistory` استفاده می‌کند. ابتدا بنیاد و سپس Identity باید در **محیط آزمایشی مجاز** اعمال شوند. هر دو `IDesignTimeDbContextFactory` صرفاً رشتهٔ اتصال ساختگی دارند و مقصد اعمال واقعی نیستند. برنامهٔ وب یا bootstrap هیچ اسکیما را خودکار اعمال نمی‌کند.

تولید **آفلاین برای بررسی، نه اجرا** با ابزار EF نسخهٔ ۱۰.۰.۱۱ و SDK سازگار با `global.json` (ابزار از NuGet رسمی لازم است):

```bash
cd ReCode
dotnet tool install dotnet-ef --tool-path "$HOME/.dotnet/tools-io" --version 10.0.11
dotnet build IO.slnx --configuration Release
for ctx in IoDbContext LoginIdentityDbContext; do
  "$HOME/.dotnet/tools-io/dotnet-ef" migrations script 0 --idempotent \
    --context "$ctx" --project src/IO.Infrastructure --startup-project src/IO.Infrastructure \
    --configuration Release --no-build --output "/tmp/$ctx-review.sql"
done
```

تولید هر دو فایل در CI بدون اتصال تست شده است؛ **اعمال خود این اسکریپت‌ها** به‌عنوان روال عملیاتی جداگانه آزمایش نشده است. در دیتابیس دارای داده، rollback حذفی و خطرناک است؛ بازیابی backup، بازبینی SQL و مجوز مقصد و برنامهٔ تغییر مستقل لازم است. اسکریپت تستی صرفاً DB تصادفی و کانتینر موقت خود را حذف می‌کند. TLS تست از گواهی خودامضا استفاده می‌کند.

ابزار `dotnet run --project src/IO.Bootstrap --configuration Release --no-build` فقط از ترمینال تعاملی اجرا می‌شود؛ لازم است connection مجاز قبلاً به‌صورت امن در محیط فرایند `ConnectionStrings__IO` تنظیم و هر دو migration جداگانه اعمال شده باشند. اپراتور باید مقصد را **پیش از اجرا** در پیکربندی امن بررسی کند؛ ابزار جزئیات اتصال را نشان نمی‌دهد. تأیید `INITIALIZE`، نام کاربر و دو بار رمز بدون echo لازم است. انتقال رمز به خط فرمان، Git، لاگ، چت یا ورودی redirectشده ممنوع است. این روش فقط اگر هر دو جدول حساب خالی باشند و قفل تراکنشی گرفته شود مدیر می‌سازد؛ نمونهٔ هم‌زمانی و PTY مصنوعی آزموده شده است. مشاهدهٔ خطای عمومی ابزار به‌تنهایی اثبات rollback در خرابی شبکه پس از commit نیست؛ پیش از تکرار، وضعیت مقصد را به‌طور امن بررسی کنید.

## کارهای الزامی پیش از تولید و تصمیم‌های باز

1. D09/D10: حدود دقیق نقش‌ها، محدودهٔ فرزند، چند نقش/جانشینی، زمان و تاریخ کسب‌وکار، ارتباط حساب با کارمند، انتساب هم‌زمان و عملیات حساس مصوب شوند؛ برای هر قابلیت جدید کنترل رکورد و عمل مستقل، نه صرفاً نمایش منو، لازم است. سیاست فعلی scope فقط یک فرض محدود و آزموده است.
2. پیکربندی TLS واقعی و گواهی مورد اعتماد، HSTS و proxyهای مورد اعتماد؛ برنامه فعلاً forwarded headers را خودکار نمی‌پذیرد. محدودساز ورود با IP مستقیم ممکن است همهٔ کاربران پشت proxy را یکی ببیند. گواهی خودامضا و `TrustServerCertificate` تست، الگوی تولید نیستند.
3. Data Protection باید با کلیدهای پایدار، اشتراکی بین نمونه‌ها، رمزگذاری‌شده، پشتیبان‌گیری و چرخش امن مدیریت شود؛ پیش‌فرض فعلی تضمین چندنمونه یا بازیابی کلید ندارد. مدیریت امن تنظیمات و حساب SQL با حداقل مجوز و آزمون بازیابی لازم است.
4. محدودسازی توزیع‌شده، کشف حملات و نام کاربری، ارزیابی زمان پاسخ، MFA، بازنشانی امن و بازیابی حساب، سیاست مدیریت رمز اولیه، کنترل نشست‌ها و تست‌های امنیتی مستقل لازم‌اند. محدودساز حافظه‌ای با restart/افزایش نمونه دور زده می‌شود. ثبت و پایش تلاش‌های ناموفق هنوز تکمیل نیست.
5. حسابرسی باید از تغییر/حذف توسط حساب عادی و دستکاری مدیر مصون‌سازی، به سامانهٔ مناسب منتقل، نگهداری و بازیابی و پوشش قبل/بعد و رخدادهای شکست بررسی شود. `SecurityAudit` موجود تنها ثبت اولیه است.
6. آزمون هم‌زمانی/بار و failure injection برای مدیریت، قفل دیتابیس، race لغو مجوز و قطعی commit، بررسی قابلیت دسترسی و مرورگرهای دیگر، و بازبینی مستقل امنیتی هنوز اجرا نشده‌اند. صفحه‌بندی فعلی offset/limit است و در تغییر هم‌زمان فهرست snapshot پایدار بین صفحات تضمین نمی‌شود.
7. تحلیل اتمی ۱٬۲۲۲ خط و بررسی قدیمی‌ها همچنان بازند. ZKTeco در دامنهٔ اصلی است ولی اتصال عملی ندارد؛ Virdi/UNIS تنها پس از امکان‌سنجی. هیچ استقرار، انتقال یا کار با دادهٔ واقعی انجام نشده است.
