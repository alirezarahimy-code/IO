# تطبیق مانیفست حضور و غیاب با TWF 4.28 و طرح ReCode

**تاریخ:** ۲۰۲۶-۱۱-۰۸  
**نوع بررسی:** تحلیل سند و متادیتای ایستا؛ نه ساخت برنامه، اتصال به SQL Server یا آزمایش رفتاری کامل.  
**مانیفست ارسالی:** [IO-manifest.md](IO-manifest.md)، نسخهٔ بدون تغییر؛ SHA-256: `4037b175dbdfea463bc140a8a4ade349dc9f46c4a32f017675b9df5a04cae129`.  
**طرح مبنا:** [README پروژه ReCode](../README.md).

## ۱. نتیجهٔ اصلی

مانیفست یک **سند نیازمندی محصول هدف** است، نه مستند اثبات‌شدهٔ رفتار نسخهٔ قدیمی. برخی اهداف آن با بازنویسی وفادار TWF هم‌جهت‌اند، اما برخی—مانند ذخیرهٔ UTC، رویداد خام تغییرناپذیر، نسخه‌گذاری قواعد و ثبت هر اجرای محاسبه—ممکن است مستلزم مدل و رفتار جدید باشند. تا زمانی که رفتار اصل بررسی و برای هر اختلاف تصمیم گرفته نشود، نباید آن‌ها را به نام «بازنویسی بدون تغییر» اعمال کرد.

.NET 10 به عنوان **هدف فنی** با مانیفست سازگار است: C#، ASP.NET Core، EF Core و SQL Server صریحاً در مانیفست ذکر شده‌اند. این تصمیم به معنی سازگاری خودکار TWF، DLLهای x86، COM، `System.Web` یا ReportViewer با Linux نیست. SDK، provider و اتصال دیتابیس در محیط فعلی آماده و آزموده نشده‌اند.

**تصمیم جدید کاربر:** TWF، T5 و Link5 از دیتابیس مشترک استفاده می‌کنند، اما محصول یکپارچهٔ جدید از صفر ساخته می‌شود و **دیتابیس آن نیز از نو طراحی می‌شود**. این ارزیابی پیش از تصمیم جدید نوشته شده و برای شواهد سیستم قدیم نگهداری می‌شود؛ [طرح جاری محصول](New-Unified-System-Plan.fa.md) بر گزینه‌های پیشنهادی قدیمی در بخش ۵ مقدم است. تعداد کاتالوگ‌ها و جزئیات محیط فعلی هنوز مشاهده نشده و هر گونه انتقال داده یا تغییر دیتابیس قدیمی نیازمند تصمیم و تأیید جداگانه است. جزئیات شواهد در [تحلیل ارتباط سه سامانه](Three-Systems-Analysis.fa.md) آمده است.

## ۳. شواهد مستقیم از دیتابیس TWF اصلی

### ۳.۱ روش و محدودیت

در DLLهای اصلی `TWF 4.28/App/bin`، منابع مدل EF شامل CSDL/MSL/SSDL به‌صورت فقط‌خواندنی تحلیل شدند. این منابع، **مدل و نگاشت زمان ساخت برنامه** را نشان می‌دهند؛ معادل مشاهدهٔ دیتابیس نصب‌شدهٔ مشتری نیستند. هنوز به هیچ SQL Server یا دادهٔ واقعی متصل نشده‌ایم، بنابراین موجودبودن واقعی جداول، نسخهٔ پایگاه داده، کلیدها/ایندکس‌های فیزیکی، داده، triggerها، permissionها و انطباق اسکیما با این مدل اثبات نشده است.

- `T5V3.DB.dll`، SHA-256: `d8f0570b39635e21b883257cf4d6bba1d6011002921ba5227dcd9cdf567b1faf`؛ منبع `EntityClasses.mdlT5V3.ssdl` دارای ۵۳ `EntitySet` ذخیره‌سازی است.
- `Personnel.dll`، SHA-256: `468e43ea66b9c591384ddcd033918e6f563a85b4caa2b6e6c4e8b85a4484050f`؛ منبع `DB.PersonnelMdl.ssdl` دارای ۲۳ `EntitySet` ذخیره‌سازی است.
- هر دو مدل از `System.Data.SqlClient` و provider manifest token `2008` نام می‌برند؛ این **نسخهٔ واقعی SQL Server نصب‌شده را مشخص نمی‌کند**.
- متدهای `MyTime3.Controllers.DBInitializer.GetT5DBInstance` و `GetPersonnelSystem` به‌ترتیب تنظیمات `T5CnnStr` و `PersonnelCnnStr` را می‌خوانند. این دو رشتهٔ تنظیمی مجزا هستند؛ تا مشاهدهٔ محیط، نمی‌توان با قطعیت گفت همیشه دو سرور یا حتی دو دیتابیس فیزیکی متفاوت‌اند.
- مدل ذخیره‌سازی فقط اشیای داخل EF آن اسمبلی‌ها را نشان می‌دهد؛ جداول دیگر، SQL دستی، stored procedure، منابع دیگر و تغییرات نصب‌شده ممکن است وجود داشته باشند.

|---|---|---|

| درخواست‌ها | `dbo.Request`: کلید `RequestID`، شناسهٔ فرد، نوع گردش‌کار، تاریخ‌ها، وضعیت تعلیق و اطلاعات تکمیلی. | نقشهٔ دقیق انواع درخواست و رفتار ثبت/لغو/ویرایش ساخته شود. |

به‌طور مشخص، `dbo.Record` در مدل قدیمی شناسهٔ صریح `ExternalEventId` ندارد و کلید مدل آن `(BadgeNumber, CheckTime)` است، نه `(DeviceId, ExternalEventId)` پیشنهادی تمرین مانیفست. این به‌تنهایی ثابت نمی‌کند هیچ مکانیزم دیگری برای تکرارزدایی در کل سامانه وجود ندارد. همچنین ستون‌های زمان نمونه در مدل قدیمی `datetime` هستند؛ این نوع به‌تنهایی مشخص نمی‌کند مقدار تاریخی به کدام منطقهٔ زمانی تعلق دارد.

### ۳.۳ نکتهٔ مهم دربارهٔ آریا

بازنویسی قبلی در `src/TWF/engine/engine-pin.json` به موتور `T5Web [3.5.7]` اشاره دارد. در بررسی قبلی، هش ۵ مورد از ۸ DLL موتور پین‌شده با DLLهای پوشهٔ `TWF 4.28` یکسان نبود. پس `schema-manifest.json` یا کد آریا **سرنخ مفید** است، ولی به‌جای مدل استخراج‌شده از DLL اصل یا بررسی دیتابیس واقعی پذیرفته نمی‌شود. تفاوت نسخه‌ها و هر دسترسی فرامرزی به کاتالوگ‌ها باید جداگانه بررسی شود.

## ۵. دیتابیس: گزینه‌های تصمیم، بدون اعمال خودکار

### گزینه A — حفظ سازگاری با دیتابیس موجود

مدل اصل با بررسی دیتابیس واقعی و آزمایشی تثبیت شود؛ لایهٔ دادهٔ .NET 10 قرارداد موجود را تا حد ممکن حفظ کند. برای الزاماتی که دادهٔ قدیمی ندارد، آن قابلیت `BLOCKED` یا با تصمیم تأییدشده در لایهٔ جداگانه بررسی شود. مزیت: کاهش ریسک سازگاری با برنامه‌های دیگر؛ محدودیت: الزامات مانیفست ممکن است تنها با همین ساختار قابل اثبات نباشند.

### گزینه B — دیتابیس موجود + جداول تکمیلی مجزا

داده و قرارداد TWF حفظ می‌شود؛ پس از تأیید، برای الزامات جدید مانند منبع رخداد، نسخهٔ قواعد یا اجرای محاسبه، جدول‌های مستقل در namespace/schema یا کاتالوگ مصوب بررسی می‌شوند. مدل مالکیت، همگام‌سازی، تراکنش، منبع حقیقت، سازگاری و مجوز نوشتن باید از قبل روشن شوند. جدول تکمیلی به‌خودی‌خود تغییرناپذیری یا سازگاری با برنامه‌های دیگر را تضمین نمی‌کند.

### گزینه C — دیتابیس جدید با انتقال کنترل‌شده

مدل جدید طبق مانیفست طراحی می‌شود؛ نقشهٔ فیلدبه‌فیلد، حفظ تاریخچه و شناسه‌ها، انتقال آزمایشی، reconciliation، backup/restore و rollback باید با دادهٔ مصنوعی و سپس با تأیید کاربر بررسی شوند. سازگاری هم‌زمان با T5/Link5 و بازگشت بدون از دست‌رفتن تغییرات خودکار نیست؛ برای آن تصمیم و طرح لازم است.

**به‌روزرسانی تصمیم:** کاربر طراحی دیتابیس جدید را برای سامانهٔ یکپارچه انتخاب کرده است؛ انتقال داده، هم‌زیستی و زمان‌بندی آن هنوز تصمیم جداگانه می‌خواهند. هیچ EF Core Migration روی دیتابیس مشترک قدیمی یا تولید بدون مجوز و نقشهٔ اثر اجرا نمی‌شود؛ گزینه‌های بالا شرح تاریخی هستند.

## ۶. مراحل تکمیلی دیتابیس در ReCode

۱. **استخراج مستندات:** با همان نسخهٔ DLLهای اصل، CSDL/MSL/SSDL هر دو مدل و تمام SQLهای دستی برنامه فهرست و به جدول/ستون/رابطه/نوع/کلید مدل نگاشت شوند؛ مسیر و هش و منشأ هر شاهد ثبت شود. نام‌های حساس بدون مقادیر واقعی گزارش شوند.
۲. **فهرست واقعی، فقط با اجازه:** در یک نسخهٔ آزمایشی ایزوله و با حساب فقط‌خواندنی، نسخهٔ SQL Server، compatibility level، schema، جدول، ستون، PK/FK، index، trigger، procedure و permissionها بررسی و با مدل مقایسه شوند. دادهٔ واقعی به گزارش یا مخزن منتقل نشود.
۳. **ردیابی وابستگی بین سامانه‌ها:** مشخص شود چه برنامه یا سرویسی خواننده/نویسندهٔ هر جدول است؛ نام اتصال و مجوز ثبت شود، نه رمز یا کلید آن. مراقبت از تغییرات هم‌زمان ضروری است.
۴. **نقشهٔ دوطرفه:** هر نیاز مانیفست به جدول/ستون و رفتار اصل، یا به شکاف و تصمیم باز متصل شود. هویت قدیم/جدید، داده‌های تهی/تکراری، زمان بدون timezone، encoding، precision و اختلاف تاریخ تعیین تکلیف شود.
۵. **طراحی و آزمون:** بر اساس گزینهٔ تأییدشده، EF Core model و migration نسخه‌دار فقط در دیتابیس تست ساخته شوند؛ برای جدول مشترک، عملیات مخرب یا تغییر کلید پیش‌فرض ممنوع است. تست یکپارچگی SQL واقعی جدا از تست in-memory ثبت شود.
۶. **کنترل استقرار:** نسخهٔ اسکیما، مقایسهٔ تعداد و checksum مناسب، consistency، زمان قطعی، backup، بازیابی آزمایشی، rollback، audit و مجوز حداقلی با سناریوهای قابل اجرا مشخص و تأیید شوند.

## ۸. معماری سه‌برنامه‌ای اعلام‌شده توسط کاربر

کاربر توضیح داده است که سه برنامه کاملاً مرتبط هستند:

- **TWF:** برای ثبت اطلاعات و در دسترس کاربران قرار دادن قابلیت‌ها.
- **T5:** برای تعریف، مدیریت و سطوح دسترسی.
- **Link5:** برنامهٔ سوم مرتبط؛ کاربر گفته است کاری مشابه انجام می‌دهد، اما تقسیم مسئولیت دقیق آن هنوز بررسی و تأیید نشده است.

کاربر علاوه بر ارتباط کاری، اشتراک دیتابیس را نیز تأیید کرده است. با این حال، تعداد کاتالوگ‌ها و جدول‌ها و سرویس‌های فعال در محیط واقعی هنوز مشاهده نشده‌اند. تا تهیهٔ نقشهٔ خواننده/نویسندهٔ واقعی، هیچ برنامه‌ای از دامنهٔ تحلیل وابستگی حذف نمی‌شود و هیچ جدول مشترکی تغییر نمی‌کند. نام «T5» نیز باید از نظر نسخه و محصول دقیق تأیید شود؛ آن را بدون شاهد با T5Web یا T5V3 یکسان فرض نمی‌کنیم. شواهد کد و مقایسهٔ مدل‌ها در [گزارش سه سامانه](Three-Systems-Analysis.fa.md) ثبت شده است.

### شاهد اولیهٔ اشتراک نام جدول‌ها با Link5

- در مخزن، `Link5 v4.0.4/Personnel.sql` شامل ۳۰ دستور `CREATE TABLE` و `Link5 v4.0.4/Link5.sql` شامل ۴۶ دستور `CREATE TABLE` شناسایی شد. این اسکریپت‌ها فقط خوانده شدند و اجرا نشدند.
- در مقایسهٔ نام‌ها، ۲۲ نام از `Personnel.sql` با نام‌های مدل تعبیه‌شده در DLLهای اصلی TWF مشترک‌اند؛ از جمله `UserInfo`, `Department`, `Device`, `TitlesChart` و `UserInfoTitles`. در `Link5.sql` نیز نام‌های `Card`, `Schedule` و `SystemLog` مشترک‌اند.
- **نام مشترک به معنی یک جدول فیزیکی، ساختار یکسان، اشتراک دیتابیس یا سازگاری نسخه‌ها نیست.** برای تأیید، باید اسکیما، کاتالوگ، رشته‌های اتصال بدون افشای رمز و تمام مسیرهای خواندن/نوشتن با مجوز و در محیط آزمایشی مقایسه شوند.
- SHA-256 اسکریپت‌ها برای ارجاع: `Personnel.sql`: `8a6954ee924e52fbfcdd1a5cc5dff1a259dacfc1ede8c81e771b4a1a77fe4a2b`؛ `Link5.sql`: `6b8d1ab38f6b4146e1d26180702695fda2e288428bdfbd3ff430b1e9a6cd3ba3`.

### پیامد برای ReCode

- در گام کشف، برای هر برنامه جدول مسئولیت، داده‌های مصرفی، داده‌های تغییرپذیر، دسترسی‌ها و وابستگی بین برنامه‌ای تهیه می‌شود.
- بازنویسی TWF نباید بدون تصمیم و تست، تعریف کاربر/سطح دسترسی یا داده‌هایی را که برنامه‌های دیگر مدیریت می‌کنند تغییر دهد.
- حفظ کارکرد هم‌زمان و شیوهٔ گذار به .NET 10 باید با سناریوی واقعی و تصمیم صریح کاربر سنجیده شود؛ هیچ جدول یا دیتابیس جدیدی به‌عنوان منبع حقیقت پیش‌فرض تعیین نشده است.

## ۹. سؤال‌ها و تصمیم‌های باز

۱. کاربر اشتراک دیتابیس سه برنامهٔ قدیمی و طراحی دیتابیس جدید برای سامانهٔ جدید را تأیید کرده است. جزئیات مسیرهای فعال Link5، نسخهٔ دقیق T5، نحوهٔ هم‌زیستی و نیاز یا عدم نیاز به انتقال اطلاعات هنوز باز است. انتقال یا تغییر محیط قدیمی نیاز به تصمیم و تأیید صریح کاربر دارد.
۲. کدام نسخهٔ واقعی SQL Server و compatibility level در محیط هدف وجود دارد؟ Linux فقط میزبان برنامه است یا سرور دیتابیس هم باید Linux باشد؟
۳. آیا نمونهٔ آزمایشیِ مستقل از اسکیما و دادهٔ مصنوعی برای مقایسه در دسترس است؟ محیط Windows/x86 ایزوله برای اجرای اصل و مقایسه وجود دارد؟
۴. برای داده‌های `datetime` قدیمی، منطقهٔ زمانی و قواعد تبدیل تاریخی چیست؟ اگر شناسهٔ بیرونی دستگاه موجود نباشد، تکرارزدایی چه معنایی دارد؟
۵. آیا خروجی payroll، نسخه‌گذاری قواعد و append-only الزام نسخهٔ اول هستند، حتی اگر با اصل تفاوت داشته باشند؟ تغییرات افزایشی باید جداگانه تصویب شوند.
۶. مدل‌ها و پروتکل‌های واقعی دستگاه‌ها، حجم و تعداد کاربران، سیاست نگهداری، نقش‌ها، مسئول تأیید فرمول‌های کار و دستمزد، و قالب سامانهٔ مقصد چیست؟
۷. محدودهٔ حقوقی استفاده از DLL، گزارش‌ها، فونت‌ها و تصاویر و همچنین رفتار مجوز/لایسنس چیست؟

## ۱۰. اقدام تا زمان پاسخ

فازهای کشف، تحلیل فقط‌خواندنی و دفتر ردیابی می‌توانند ادامه یابند. ساخت/تغییر دیتابیس، migration، انتقال داده، اتصال به سیستم تولید یا اعمال الزام جدید به‌عنوان رفتار اصل تا تعیین تکلیف و تأیید متوقف است. مانیفست مبنای نیازمندی‌های محصول باقی می‌ماند، ولی تفاوت‌های آن با TWF در دفتر تصمیم ثبت می‌شوند.
